# Переход потребителей Blog API v1 на Media

Потребители v1 обновляют схемы ответов по [полному OpenAPI](openapi-v1.yaml)
и [TypeScript DTO](frontend-api-types.ts). Версия пути остаётся `/api/v1`.
Для клиентов со строгими валидаторами это согласованное обновление API и клиента:
старые схемы с `additionalProperties: false` отклонят новые поля.

| Ответ | Изменение |
| --- | --- |
| `Me` | Обязательные `avatar` (объект или null) и `avatarVersion` (UUID, в том числе без аватара) |
| `AuthorRef` | Обязательное nullable `avatar` в публикациях и комментариях |
| Карточки публикаций | Обязательное nullable `coverFileId`. `coverUrl` может быть относительным URL Blog |
| Детали публикаций | Обязательные `inlineImages` и `attachments`, пустые при отсутствии связей |
| Детали workspace | Также обязательные `inlineImageIds` и `attachmentIds` |

У публичных Hidden/Deleted комментариев сохраняется `author: null`.
Отдельное поле аватара в таких ответах отсутствует.

Старые JSON payloads для create и PUT остаются допустимыми. При PUT пропуск
`coverFileId`, `inlineImageIds` и `attachmentIds` сохраняет управляемые связи.
Передавайте `coverFileId: null` или пустой массив, чтобы снять соответствующую
связь. Массивы принимают только значения-массивы. Для внешней обложки применяется
прежнее правило очистки при пропуске `coverUrl`. Точное эхо текущего управляемого
`coverUrl` при пропуске `coverFileId` сохраняет связь.

## Порядок переключения

1. В deployment evidence перечислите все поддерживаемые установки и версии
   клиентов v1, включая строгие валидаторы, с владельцем и результатом smoke
   для каждого. В репозитории переход проверяют потребительские тесты MVP и Media.
2. Соберите совместимые версии клиентов из полного контракта. В стенде выполните
   `dotnet test tests/BlogEngine.IntegrationTests -c Release --filter Category=ConsumerContract`.
   Проверка OpenAPI сопоставляет схемы, полученные из обработчиков, и опубликованный
   документ. HTTP walkthrough проверяет legacy PUT и полный маршрут загрузки,
   скачивания, чтения квоты, привязки и смены аватара.
3. Во время [переключения](../operations/deployment.md) обновите API и всех
   поддерживаемых клиентов при закрытой внешней записи. Для каждой версии
   проверьте strict decode `Me`, публикаций и комментариев, затем загрузку,
   получение байтов и версионное обновление. Проверьте readiness с production
   конфигурацией и сохраните исход smoke по каждому клиенту.
4. Открывайте запись после выполнения production gate из
   [эксплуатационного контракта](../../specs/002-files-avatars/contracts/operations.md#переключение-на-media).
