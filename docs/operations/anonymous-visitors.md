# Анонимные посетители и учёт просмотров

Потребитель явно вызывает bodyless `POST /api/v1/publications/{id}/views` после
открытия Published-материала. GET ленты, материала, комментариев и счётчиков ничего
не регистрирует. Успешный ответ: `counted`, накопленный `viewCount` и
`anonymousVisitorId`. Ответы имеют `Cache-Control: private, no-store`.

Анонимный потребитель сохраняет непрозрачный `anonymousVisitorId` и повторяет его
в `X-Anonymous-Visitor`. Движок не устанавливает cookies. Отсутствующее,
непригодное, поддельное или длиннее 256 символов значение заменяется новым
только в успешном ответе. Потеря значения означает нового посетителя; это защита
от повторов стабильной личности, а не средство защиты от ботов.

Проверенный Bearer всегда имеет приоритет: используется локальный ID пользователя
на всех устройствах, а `anonymousVisitorId` равен `null`. Анонимная история после
входа не объединяется; возможно по одному анонимному и вошедшему просмотру.
Неверный переданный Bearer даёт 401; недоступная необходимая проверка ключа — 503.
Закрытый, удалённый или отсутствующий материал даёт 404 без visitor token.

Для каждой пары материал–посетитель учитывается одно открытие за 24 часа от
последнего учтённого T. Повтор до границы не сдвигает T. Равенство `T + 24 h`
разрешает новое открытие. Время — PostgreSQL `clock_timestamp()` после получения
блокировки публикации; все реплики используют одну БД. Dedup-запись и bigint
счётчик фиксируются одной транзакцией. Версия и даты редактирования не меняются.

## Настройка и ротация ключей

API требует `AnonymousVisitors:ActiveKeyId` и map `AnonymousVisitors:Keys:<keyId>`.
Каждый ID содержит 1–32 ASCII-буквы, цифры, `_` или `-`; точки запрещены.
Каждый секрет — base64 ровно 32 криптографически случайных байтов. Активный ID
должен присутствовать в непустом map. Ошибка любого элемента запрещает запуск.
Operator эти настройки не использует.

Секреты поступают через защищённую конфигурацию среды; локально допустимы
user-secrets API. Их нельзя хранить в appsettings, Git, командных аргументах,
shell history или отчётах. HMAC key ring отделён от RSA-ключей Identity.
У всех реплик должны быть одинаковые key ring и активный ID.
Изменения key ring и активного ID применяются при перезапуске/развёртывании API;
проверяйте конфигурацию каждой реплики на каждом шаге ротации.

Безопасная последовательность ротации:

1. Добавить новый ключ в защищённый key ring всех реплик, оставив прежний активным.
2. Убедиться, что каждая реплика принимает оба ключа; затем переключить активный ID.
3. Сохранять прежний ключ, пока требуется принимать выданные им visitor tokens.
4. Удалять прежний ключ согласованно со всех реплик. Его tokens станут непригодными,
   и следующий анонимный запрос получит новую личность, даже внутри прежнего окна.

Формат — `v1.<keyId>.<random256>.<mac>`. Payload и HMAC-SHA256 имеют canonical
base64url без padding; MAC подписывает UTF-8 префикс до последней точки и
сравнивается за постоянное время. Выпущенный token не длиннее 123 символов.
Dedup хранит только SHA-256 типизированного стабильного payload либо локального UUID.
Переподпись одного payload другим сохранённым ключом не меняет личность.
Token не имеет срока истечения: 24 часа относятся к окну учёта, а не к подписи.

## Очистка и развёртывание

Каждая API-реплика запускает worker каждые 15 минут. Одна транзакция выбирает
не более 500 истёкших кандидатов по индексу `(last_counted_at, publication_id)`.
До блокировки дочерних строк worker блокирует публикации в UUID ASC, повторно
берёт время БД и проверяет возраст перед удалением. Если регистрация успела
продлить окно, запись сохраняется. Несколько workers безопасны.

Команды БД ограничены пятью секундами; общий срок партии — десять секунд.
Остановка host отменяет ожидание таймера и выполняющуюся партию, откатывая её.
Сбой очистки оставляет лишние истёкшие строки и пишет безопасное предупреждение.
Очистка не меняет накопленный `viewCount`, контент или publication tombstones.
При большом хвосте истёкших записей очистка продолжается следующими партиями
по расписанию; это не меняет правило регистрации.

Перед запуском US7 применить `AddViewDeduplication` отдельными migration credentials,
затем повторить [`permissions.sql`](../../ops/database/permissions.sql).
Миграция добавляет новую пустую таблицу и индекс без переписывания контента.
Runtime получает SELECT/INSERT/UPDATE/DELETE этой таблицы, без DDL; Operator
не получает доступа к Engagement. Приложение не применяет миграции при старте.
Откат удаляет только активную дедупликацию, сохраняя агрегат: повторное включение
после такого отката может повторно учесть посетителей прежнего окна. Для сохранения
окна оставьте схему и ключи при откате бинарника; destructive Down допустим только
на изолированной копии либо при согласованной потере активных окон.

Нельзя журналировать `X-Anonymous-Visitor`, visitor token/ID/хеш, key ring или request
body. Диагностика API содержит только безопасные route/status/trace поля; worker
пишет тип сбоя без SQL, параметров или exception message.
