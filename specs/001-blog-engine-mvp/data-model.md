# Модель данных: Blog Engine MVP

Дата: 2026-10-24. Основание: [spec.md](spec.md) и принятые решения
[research.md](research.md), прежде всего R-02–R-06 и R-08.
Это проект модели и транзакционных правил; миграции и проверки PostgreSQL
в рамках планирования ещё не выполнялись.

## 1. Владение моделью и общие соглашения

Четыре production-проекта: `BlogEngine.Core`, `BlogEngine.Infrastructure`,
`BlogEngine.Api`, `BlogEngine.Operator`. Core содержит Domain/Application модулей
Accounts, Publishing, Discussions, Engagement и координирующие ReadModels.
Infrastructure отображает модель в PostgreSQL через один EF Core DbContext
и одну последовательность миграций. Api и Operator собирают свои hosts.
EF-сущности не являются HTTP DTO; детали EF/Npgsql не входят в Core.

Физические имена ниже используют `snake_case`, таблицы распределены по схемам
`accounts`, `publishing`, `discussions`, `engagement`. Схема отражает владельца,
а не отдельную БД или отдельный DbContext. Дочерний модуль не получает права
произвольно изменять чужие таблицы через общий контекст.

- Системные ID и редактируемые `version`: PostgreSQL `uuid`, C# `Guid`;
  генерируются системой, не назначаются клиентом. Версия — новый непрозрачный
  UUID при каждой успешной содержательной записи, не порядковый номер.
- Моменты времени: `timestamptz`, C# `DateTimeOffset` с offset 0; UTC во всех
  соединениях. Значения от клиента не принимаются. Production-время назначается
  портом времени БД; для окна просмотров используется `clock_timestamp()` после
  получения блокировки, а не время начала ожидающей транзакции.
- PostgreSQL 18, UTF-8, collation `C`, без дополнительных расширений.
  Сортировка ID — штатный порядок PostgreSQL `uuid`; ID разрешает совпадения дат.
- Строковые лимиты в символах считаются по Unicode scalar values, как
  PostgreSQL `char_length`, а не по числу UTF-16 code units. Markdown ограничен
  отдельно через `octet_length` в UTF-8. Недопустимый для PostgreSQL U+0000
  отклоняется на границе API с ошибкой поля.
- Для title/name/comment используется trim по явному набору Unicode White_Space:
  U+0009–U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000–U+200A,
  U+2028–U+2029, U+202F, U+205F, U+3000. Прикладной валидатор и row-level CHECK
  используют один набор; SQL CHECK может использовать `btrim` с этим набором.
  Markdown сохраняется без trim; тем же набором только проверяется непустота
  при публикации. Slug не приводится к регистру и не обрезается: неверный ввод
  отклоняется.
- Все CHECK/FK/UNIQUE получают стабильные имена для безопасного преобразования
  известных нарушений в коды ошибок. Nullable означает отсутствие значения;
  проверки, требующие значения, дополняются NOT NULL.
- Прямые неограниченные списки сущностей, lazy loading и выдача EF-графа запрещены.
  Чтение использует DTO-проекции/AsNoTracking и серверную фильтрацию.

## 2. Accounts

### `accounts.local_users`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid, PK | Непрозрачный стабильный публичный ID автора |
| `issuer` | text, NOT NULL | Точный проверенный issuer единственной настроенной установки Identity |
| `subject` | uuid, NOT NULL | Единственный проверенный `sub` внешнего пользователя |
| `created_at` | timestamptz, NOT NULL | Момент первого успешного bootstrap |

UNIQUE `(issuer, subject)`, CHECK непустого issuer. Ни email, ни `sid`, ни
`client_id`, ни токен не являются ключом или сохраняемым профилем.
Связь после создания неизменяема. HTTP CRUD пользователей и удаление локальной
связи не входят в MVP. FK из материалов, комментариев и лайков используют RESTRICT.
Публичная ссылка на автора содержит только `id`; отдельного публичного профиля нет.

Reader — обязательное неявное право каждой существующей проверенной LocalUser,
поэтому строка назначения Reader не хранится и не может быть отозвана оператором.

### `accounts.role_assignments`

| Поле | Тип | Правило |
|---|---|---|
| `user_id` | uuid, FK, NOT NULL | Существующая LocalUser |
| `role` | smallint, NOT NULL | Только Author=1, Moderator=2, Admin=3 |
| `granted_at` | timestamptz, NOT NULL | Время назначения |

PK `(user_id, role)` исключает повторное назначение; CHECK ограничивает роль,
FK `user_id` → LocalUser с RESTRICT. Reader не является допустимым значением.
Author и Moderator независимы; Admin даёт все права при вычислении политики,
без создания дополнительных строк назначений.

HTTP credential имеет SELECT на назначения и не имеет INSERT/UPDATE/DELETE.
Operator credential меняет только повышенные назначения существующих пользователей
и записывает аудит; DDL и доступ к Identity ему не предоставляются.
Роли читаются из PostgreSQL в начале каждой защищённой операции без role cache.
Начатая после commit отзыва операция применяет новые права; уже выполняемая
использует свой начальный authorization snapshot.

### `accounts.role_change_audit`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid, PK | ID записи аудита |
| `command_correlation_id` | uuid, NOT NULL, UNIQUE | ID конкретного выполнения CLI-команды; ключ проверки неизвестного commit-результата |
| `target_user_id` | uuid, FK, NOT NULL | Существующая LocalUser, RESTRICT |
| `role` | smallint, NOT NULL | Author/Moderator/Admin, как в RoleAssignment |
| `action` | smallint, NOT NULL | Grant=1 или Revoke=2 |
| `changed` | boolean, NOT NULL | Изменилось ли фактическое назначение |
| `actor` | text, NOT NULL | Локальная OS/deployment identity выполняющего Operator |
| `reason` | text, NOT NULL | Обязательная причина команды, 1–512 Unicode scalar values после trim |
| `occurred_at` | timestamptz, NOT NULL | UTC-время изменения/идемпотентного результата |

CHECK допустимых role/action, непустого actor и нормализованной длины reason
1–512 символов. UNIQUE command_correlation_id делает поиск результата конкретной
команды однозначным и создаёт необходимый индекс. Версионируемая модель не
хранит пароли, connection strings или токены оператора. Назначение/отзыв и аудит
фиксируются в одной транзакции; повтор grant существующей роли или revoke
отсутствующей успешен, `changed=false`, но имеет запись аудита.
Operator получает INSERT и SELECT соответствующих записей аудита для проверки
результата команды по correlation ID, без UPDATE/DELETE; HTTP runtime не
получает SELECT/INSERT/UPDATE/DELETE к аудиту. Публичного API аудита нет.

### Bootstrap и конкурентные назначения

После полной проверки JWT выполняются `INSERT ... ON CONFLICT (issuer, subject)
DO NOTHING` и затем SELECT существующей связи отдельным READ COMMITTED statement.
Одна транзакция завершает bootstrap; неявный Reader не требует второй вставки.
Нельзя объединять INSERT и fallback SELECT в один CTE/UNION: конкурентная
победившая строка может вызвать DO NOTHING, оставаясь невидимой snapshot этого
statement. Следующий statement видит её после ожидания победителя.

Operator сначала находит существующую LocalUser и получает transaction-scoped
advisory lock по её local UUID; несколько команд для одного пользователя
сериализуются этим замком без UPDATE-привилегии на LocalUser. Отображение UUID
в ключ замка стабильно для всех процессов; коллизия может только дополнительно
сериализовать разных пользователей. Затем Operator изменяет назначение
идемпотентно и добавляет RoleChangeAudit. Неизвестный пользователь не создаётся.
HTTP bootstrap никогда не выдаёт повышенных прав.

## 3. Publishing

### `publishing.publications`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid, PK | Системный ID материала |
| `author_id` | uuid, FK, NOT NULL | Неизменный владелец, LocalUser |
| `title` | text, NOT NULL | После trim 1–200 символов |
| `slug` | text, NOT NULL, UNIQUE | Строгий формат и длина 1–120 |
| `markdown` | text, NOT NULL | До 1 048 576 байт UTF-8; пустой допустим только в Draft |
| `description` | text, NULL | До 500 символов |
| `cover_url` | text, NULL | До 2048 символов; абсолютный HTTPS URI |
| `state` | smallint, NOT NULL | Draft=0, Published=1 |
| `created_at` | timestamptz, NOT NULL | Назначается при создании |
| `updated_at` | timestamptz, NOT NULL | Последняя содержательная запись |
| `first_published_at` | timestamptz, NULL | Назначается один раз при первой публикации |
| `deleted_at` | timestamptz, NULL | Терминальная метка удаления |
| `version` | uuid, NOT NULL | Версия редактирования/жизненного цикла/классификации |
| `like_count` | bigint, NOT NULL, default 0 | Текущее число действующих лайков |
| `view_count` | bigint, NOT NULL, default 0 | Накопленные учтённые открытия |

DB CHECK закрепляют длины title/description/cover, нормализованный непустой title,
`octet_length(markdown) <= 1048576`, допустимое state, неотрицательные счётчики,
а также `Published ⇒ first_published_at IS NOT NULL` и непустой после проверки
пробелов Markdown. Slug имеет CHECK
`char_length(slug) BETWEEN 1 AND 120 AND slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'`.
`author_id` → LocalUser с RESTRICT. Полная проверка абсолютного HTTPS URI выполняется
на границе системы; CHECK длины и HTTPS-префикса служит дополнительной защитой,
но не подменяет URI parser. Загрузка обложки отсутствует.

Уникальность slug глобальна для всех строк, включая `deleted_at IS NOT NULL`;
частичный UNIQUE только для активных строк запрещён. Изменение slug допустимо
только пока `first_published_at IS NULL`; неизменность после первой публикации,
владельца и первой даты защищает доменное правило внутри заблокированной записи.
Обычный CHECK текущей строки не проверяет её предыдущее значение.

Публичный предикат в каждой операции чтения/взаимодействия:
`state = 1 AND deleted_at IS NULL`. Его применяют до выдачи тела, счётчиков,
версии, комментариев или результата реакции; отсутствие и недоступность дают 404.
Рабочий список применяет `deleted_at IS NULL` и разрешённую область владельца/Admin.

Счётчики физически находятся здесь для индекса популярности. Их содержательное
владение остаётся у Engagement; запись происходит только через разрешённый
контракт Publishing в общей транзакции. Она не меняет `updated_at`/`version` и
не перезаписывает контент. Редактирование контента также не отправляет старые
значения счётчиков в UPDATE. Нет параллельной таблицы статистики/read-replica
с копией state/first_published_at.

### Жизненный цикл материала

| Из состояния | Команда | Результат |
|---|---|---|
| Не существует | Create | Draft, системный владелец/даты, first_published_at=NULL, счётчики 0 |
| Draft до первой публикации | Edit | Допустимы контент, slug и назначения; новая version |
| Draft | Publish | Непустой Markdown; Published; first_published_at назначается только если NULL |
| Published | Edit | Изменения видны сразу; Published/slug/first_published_at сохраняются |
| Published | Unpublish | Draft; обсуждение и реакции сохраняются, публично недоступны |
| Draft после публикации | Edit/Publish | Slug/первая дата неизменны; Publish вновь открывает сохранённые взаимодействия |
| Уже в желаемом активном состоянии | Повтор Publish/Unpublish с текущей version | Успех без смены version/updated_at/первой даты |
| Любое активное | Delete | deleted_at назначен; новая version; назначения справочников сняты |
| Удалено | Любая продуктовая команда | Недоступно; восстановления и повторного использования slug нет |

Публикация не планируется на будущее. Удаление оставляет внутренний tombstone
и связанные данные без публичного доступа. Последние state/контент/первая дата
могут сохраняться внутри строки; `deleted_at` всегда имеет приоритет. Административного
обхода терминального удаления нет. Удаление не выполняет неограниченный cascade
обсуждения и не оставляет назначения, блокирующие удаление справочника.

### Категории, теги и назначения

`publishing.categories` и `publishing.tags` имеют одинаковую форму:

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid, PK | Системный ID |
| `name` | text, NOT NULL | После trim 1–80 символов |
| `slug` | text, NOT NULL | Формат Publication.slug, неизменен после создания |
| `version` | uuid, NOT NULL | Меняется при переименовании |

Каждый справочник имеет свой UNIQUE slug и CHECK name/slug. Одинаковый slug в
разных справочниках допустим; уникальность имени не требуется.
Удаление справочника физическое, требует текущей версии и отсутствия назначений.
FK RESTRICT является окончательной защитой гонки назначения/удаления.

`publishing.publication_categories(publication_id uuid, category_id uuid)` и
`publishing.publication_tags(publication_id uuid, tag_id uuid)` имеют composite PK
по обоим полям, NOT NULL и FK RESTRICT к обеим сторонам. Удаление материала
снимает свои joins явной ограниченной операцией; внешний материал не удаляется
физически в продуктовых сценариях. Переименование справочника отражается в
проекциях связанных материалов без копирования имени в join.

Кардинальности 0–5 категорий/0–20 тегов, существование назначаемых ID и отсутствие
повторов проверяются приложением при удержании блокировки публикации. Это
межстрочные правила: ложный CHECK с подзапросом в другие строки не используется.
Одна замена назначений и контента атомарна и меняет version материала.

## 4. Discussions

### `discussions.comments`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid, PK | Системный ID комментария |
| `publication_id` | uuid, FK, NOT NULL | Неизменный материал |
| `parent_id` | uuid, NULL | Неизменный непосредственный родитель |
| `author_id` | uuid, FK, NOT NULL | Неизменный автор, LocalUser |
| `depth` | smallint, NOT NULL | Корень=1, максимум 5 |
| `state` | smallint, NOT NULL | Visible=0, Hidden=1, Deleted=2 |
| `text` | text, NULL | После trim 1–5000 символов у Visible/Hidden; NULL у Deleted |
| `created_at` | timestamptz, NOT NULL | Неизменно |
| `updated_at` | timestamptz, NOT NULL | Последнее редактирование/модерация/удаление |
| `edited_at` | timestamptz, NULL | Меняется только при изменении текста |
| `version` | uuid, NOT NULL | Версия текста и модерационного состояния |
| `visible_descendant_count` | bigint, NOT NULL, default 0 | Число всех потомков в Visible, без самого узла |

CHECK ограничивают state/depth/count, задают
`(parent_id IS NULL) = (depth = 1)`, исключают `parent_id = id`, проверяют
`Deleted ⇒ text IS NULL` и `Visible/Hidden ⇒ text IS NOT NULL` с допустимой
нормализованной длиной. FK публикации/автора — RESTRICT. Помимо PK существует
UNIQUE `(publication_id, id)`, на который ссылается composite FK
`(publication_id, parent_id)` → `(publication_id, id)` с RESTRICT. NULL parent
обозначает корень; составной FK исключает родителя другого материала.

Правило `depth = parent.depth + 1`, видимый неудалённый родитель и запрет смены
publication/parent/author обеспечиваются приложением после блокировки материала.
Родитель уже существует до вставки, а reparent отсутствует, поэтому цикл не
может возникнуть допустимой командой. Нет физического удаления отдельного узла:
удаление текста сохраняет структурные FK и потомков.

### Переходы комментария и видимость дерева

| Исходное состояние | Действие | Новое состояние/текст | Дельта видимых узлов для предков |
|---|---|---|---|
| Новый | Reader создаёт | Visible, непустой текст | +1 |
| Visible | Автор/Admin редактирует | Visible, новый текст, edited_at | 0 |
| Visible | Moderator/Admin скрывает | Hidden, исходный текст сохранён | −1 |
| Hidden | Moderator/Admin восстанавливает | Visible, сохранённый текст | +1 |
| Hidden | Admin редактирует | Hidden, новый текст, edited_at | 0 |
| Visible | Автор/Admin удаляет | Deleted, text=NULL | −1 |
| Hidden | Автор/Admin удаляет | Deleted, text=NULL | 0 |
| Deleted | Автор/Admin повторяет Delete с текущей version | Успех без смены version/updated_at; text остаётся NULL | 0 |
| Deleted | Редактирование/восстановление | Запрещено, текст не восстанавливается | 0 |

Автор без Admin не редактирует Hidden, но может удалить свой текст. Право
владения публикацией не даёт права менять/модерировать чужой комментарий.
Все команды обсуждения требуют живого Published-родителя. Moderator/Admin
получает модерационный список комментариев только таких материалов.

При изменении принадлежности узла к Visible ровно ±1 добавляется каждому его
предку, максимум четырём. Собственные видимые потомки скрываемого/удаляемого
узла остаются видимыми, поэтому их количество не вычитается. Derived count не
меняет version/updated_at предков: это не редактирование их текста/состояния.
Все изменения узла и предков входят в одну транзакцию; CHECK count >=0 ловит
нарушение, а интеграционный тест сравнивает агрегат с фактическими состояниями.

Публичная включаемость узла: `state = Visible OR visible_descendant_count > 0`.
Hidden/Deleted без видимых потомков не занимают место на странице. Включённый
Hidden/Deleted проецируется в нейтральную заглушку без текста/автора; для него
сохраняются structural ID/parent/depth и предусмотренные контрактом даты.
`hasReplies` — EXISTS непосредственного ребёнка с тем же предикатом включаемости.
Так видимый внук достижим через последовательность заглушек, а большое скрытое
поддерево не загружается и не обходится целиком на каждом чтении.

Корни и прямые ответы читаются отдельными ограниченными страницами. Ответ
на публично включённую заглушку всё равно запрещён: отвечать можно только на
реальное состояние Visible. Повторная публикация открывает сохранённое дерево
без пересчёта count; публикационное состояние не меняет внутренний state узлов.

## 5. Engagement

### `engagement.likes`

| Поле | Тип | Правило |
|---|---|---|
| `publication_id` | uuid, FK, NOT NULL | Существующий материал |
| `user_id` | uuid, FK, NOT NULL | Проверенная LocalUser |
| `created_at` | timestamptz, NOT NULL | Время первого установления текущего лайка |

PK `(publication_id, user_id)` — единственный активный лайк пары; FK — RESTRICT.
История постановок/снятий не хранится. Public liked-by/user lists отсутствуют.
`isLikedByCurrentUser` вычисляется correlated EXISTS для проверенного локального
пользователя; анонимно задаётся false, не загружается список поставивших лайк.

### `engagement.view_deduplication_records`

| Поле | Тип | Правило |
|---|---|---|
| `publication_id` | uuid, FK, NOT NULL | Существующий материал |
| `visitor_kind` | smallint, NOT NULL | Authenticated=1, Anonymous=2 |
| `visitor_key` | bytea, NOT NULL | 32 байта SHA-256 типизированного стабильного ID |
| `last_counted_at` | timestamptz, NOT NULL | Только последнее учтённое открытие |

PK `(publication_id, visitor_kind, visitor_key)`, CHECK допустимого kind и
`octet_length(visitor_key) = 32`, FK публикации — RESTRICT. Строка не является
историей всех открытий и не участвует в восстановлении накопленного view_count.
Хеш локального user UUID не имеет FK на LocalUser; принадлежность устанавливает
проверенный контекст до вызова persistence-порта.

Для Authenticated стабильный ID берётся из LocalUser; для Anonymous — из
случайного 256-битного payload проверенного token
`v1.<keyId>.<random256>.<mac>`. До хеширования применяется однозначное
типизированное кодирование/разделение доменов. Хешируется стабильный payload,
а не всё подписанное представление, чтобы смена HMAC-ключа сама по себе не
создавала другую личность. Token/key ring/HMAC secrets в этой таблице не хранятся.
Отсутствующий/непригодный anonymous token заменяется новым, выданным движком.
Bearer имеет приоритет; анонимная и вошедшая история не объединяются.

### Транзакция лайка

1. В начале операции прочитать актуальные локальные права; для записи нужен Reader.
2. Начать READ COMMITTED, через Publishing заблокировать материал FOR UPDATE;
   после ожидания снова проверить Published и отсутствие deleted_at.
3. Установка: INSERT с ON CONFLICT DO NOTHING RETURNING. Снятие: DELETE RETURNING.
4. Только если изменилась одна строка, Publishing атомарно меняет like_count
   на +1/−1. Повтор желаемого состояния успешен с нулевой дельтой.
5. Commit фиксирует источник и агрегат вместе; ошибка откатывает оба.

Лайк не требует версии материала: его идемпотентность задаёт ресурс текущего
пользователя. Смешанные конкурентные установки/снятия имеют порядок получения
блокировки, итоговый like_count равен числу действующих строк после завершения.

### Транзакция открытия

1. Определить доверенную локальную либо выданную анонимную личность.
2. Начать транзакцию, заблокировать и проверить материал тем же способом.
3. Один раз получить T через порт production-времени БД после блокировки.
4. Условный UPSERT создаёт строку либо обновляет `last_counted_at = T` только
   когда существующее `last_counted_at <= T - interval '24 hours'`.
5. Только возвращённая INSERT/UPDATE строка означает дельту view_count +1;
   WHERE=false не возвращает строку и не сдвигает окно.
6. Изменение dedup и view_count фиксируется одним commit.

Равенство границе допустимо; используется 24 часа, не календарный `1 day`.
Обычные GET ленты/материала/комментариев/счётчиков этот алгоритм не вызывают.
Переполнение bigint/ошибка БД откатывает регистрацию и не возвращает успех.

### Ограниченная очистка dedup

HostedService запускается каждые 15 минут и обрабатывает не более 500 кандидатов
за транзакционную партию; CancellationToken и ограниченные таймауты обязательны.
Кандидаты выбираются по expiry-индексу без предварительной блокировки dedup.
Для партии publication IDs сортируются и блокируются в общем порядке; затем
T берётся из БД и возраст кандидата повторно проверяется перед DELETE.
Удаляется только строка, всё ещё удовлетворяющая
`last_counted_at <= T - interval '24 hours'`.

Если открытие обновило строку первым, повторная проверка сохраняет её. Если
очистка удалила просроченную строку первой, следующая регистрация создаёт новую
и учитывает допустимое открытие. Несколько workers безопасны; source record
не блокируется до publication row, чтобы не инвертировать порядок блокировок.
Очистка никогда не меняет view_count и не удаляет публикационные tombstones.
Отказ worker оставляет только лишние истёкшие записи, не ослабляя дедупликацию.

## 6. Версии, атомарность и межстрочные инварианты

`version` Publication/Comment/Category/Tag возвращается в соответствующих DTO.
Изменение, удаление, публикация/снятие с публикации и модерационный переход
требуют `X-Resource-Version: <UUID>` целевого ресурса. Отсутствие/неверный формат
— 400; несовпадение — `409 concurrency_conflict` без записи. Version — не ETag
полного HTTP-представления; счётчики и состав связанных справочников могут
меняться независимо. Created DTO содержит первую version.

EF помечает поле concurrency token. Даже после блокировки сравнивается версия,
предоставленная клиентом, а не только автоматически загруженная свежая версия;
UPDATE/DELETE должен сохранять условие исходной версии. При конфликте не
выполняется слепой retry содержательного изменения. Проверка прав и доступности
предшествует раскрытию версии/деталей конфликта.

У каждого сценария одна минимальная транзакционная граница:

- Создание публикации: строка + максимум 25 назначений. UNIQUE slug решает гонку
  создания; ожидаемое нарушение переводится в `409 slug_conflict`.
- Изменение/переход/удаление публикации: блокировка её строки → доступ/владение/
  версия → контент/назначения/состояние → новая version → commit.
- Любая запись комментария: строка публикации → её публичность → целевой узел/
  родитель/неизменность ссылок/права/версия → узел и максимум четыре предка → commit.
- Реакции и очистка: строка публикации → дочерняя строка → агрегат; рецепты выше.
- Переименование/удаление справочника: блокировка целевой строки → Admin/версия →
  UPDATE/DELETE; FK RESTRICT окончательно предотвращает удаление назначенного ID.
  Справочник при назначении не блокируется FOR UPDATE после материала; FK-замки
  и ограничения сохраняют целостность. Известные FK-ошибки дают стабильный конфликт.
- Operator: найденная LocalUser → transaction advisory lock по local UUID →
  назначения → неизменяемый audit. HTTP не меняет назначения.

Для Publish/Unpublish, Hide/Restore и повторного Delete уже Deleted-комментария
сначала проверяются доступ/права и предоставленная version, затем желаемое
состояние. При текущей version уже достигнутое допустимое состояние успешно
возвращается без ротации version, изменения updated_at/edited_at, первой даты
или derived counters. Устаревшая version всегда даёт 409, даже если желаемое
состояние уже достигнуто. Deleted нельзя Hide/Restore/редактировать; удалённый
материал остаётся недоступен, повтор его Delete не является этой no-op-командой.

Если операция затрагивает несколько публикаций, их FOR UPDATE берутся по UUID
по возрастанию. Стандартные операции работают с одной публикацией. Не допускаются
долгие пользовательские паузы, исходящий HTTP или JWKS fetch внутри транзакции.
READ COMMITTED после ожидания возвращает актуальную строку; состояние проверяется
повторно внутри блокировки. Таймаут/отмена/неожиданный deadlock откатывает всё;
клиент не получает ложного успешного результата.

DB-ограничения покрывают доступные row-level/ссылочные/уникальные инварианты.
Равенство агрегатов источникам, ограничение числа назначений, глубина относительно
родителя, терминальность удаления и неизменность прошлых значений — явно
межстрочные/исторические правила приложения, проверяемые под указанной защитой.
CHECK с обращением к другим строкам не используется. Production HTTP credential
не имеет DDL; схема изменяется отдельным миграционным шагом.

## 7. Индексы и ограниченные проекции

Индексы создаются миграциями; итоговые SQL/планы проверяются EXPLAIN на seed SC-005.
Имена ниже обозначают состав индекса, а не требуют дублировать уже созданный
индекс PK/UNIQUE. Предикаты публичности используют точные константы и ту же форму
в запросах, чтобы PostgreSQL распознавал частичный индекс.

| Таблица | Индекс/ограничение | Запрос |
|---|---|---|
| local_users | UNIQUE `(issuer, subject)` | Проверенная внешняя связь/bootstrap |
| role_assignments | PK `(user_id, role)` | Актуальные права пользователя |
| role_change_audit | `(target_user_id, occurred_at DESC, id DESC)` | Ограниченный эксплуатационный аудит, без HTTP endpoint |
| role_change_audit | UNIQUE `(command_correlation_id)` | Однозначная проверка outcome_unknown после потери commit-ответа |
| publications | UNIQUE `(slug)` без active-предиката | Чтение по slug и вечная резервация |
| publications | `(first_published_at DESC, id DESC)` WHERE state=1 AND deleted_at IS NULL | Свежая публичная лента |
| publications | `(like_count DESC, first_published_at DESC, id DESC)` с тем же WHERE | Популярная публичная лента |
| publications | `(author_id, updated_at DESC, id DESC)` WHERE deleted_at IS NULL | Рабочий список Author |
| publications | `(updated_at DESC, id DESC)` WHERE deleted_at IS NULL | Рабочий список Admin |
| categories/tags | UNIQUE `(slug)`; `(name, id)` | Адрес/порядок публичного справочника |
| publication_categories | PK `(publication_id, category_id)`; `(category_id, publication_id)` | Batch назначения, фильтр и FK RESTRICT |
| publication_tags | PK `(publication_id, tag_id)`; `(tag_id, publication_id)` | Batch назначения, фильтр и FK RESTRICT |
| comments | UNIQUE `(publication_id, id)` | Цель составного self-FK |
| comments | `(publication_id, parent_id, created_at, id)` WHERE state=0 OR visible_descendant_count>0 | Ограниченные публичные корни/прямые ответы и hasReplies |
| comments | `(publication_id, parent_id)` | Проверка self-FK и непубличные связи |
| comments | `(created_at DESC, id DESC)` | Модерация без фильтра материала/состояния |
| comments | `(publication_id, state, created_at DESC, id DESC)` | Модерация с фильтрами материала/состояния |
| likes | PK `(publication_id, user_id)` | Идемпотентная реакция, EXISTS персонализации |
| view_deduplication_records | PK `(publication_id, visitor_kind, visitor_key)` | Условный UPSERT пары |
| view_deduplication_records | `(last_counted_at, publication_id)` | Ограниченная партия истёкших кандидатов |

При проверке планов отдельно оцениваются рабочий список с state, модерация
только по state/только по publication_id и глубокие страницы. Дополнительный
индекс вводится по измеренной селективности/плану, а не как обязательное
дублирование всех комбинаций. FK author/user не требуют растущих пользовательских
списков: удаления LocalUser и соответствующих запросов в MVP нет.

Все списки используют page >=1, pageSize по умолчанию 20, максимум 100;
недопустимый ввод — 400. Offset `(page-1)*pageSize` вычисляется проверяемым int64,
передаётся параметром SQL без сужения в EF Skip(int). Запрашивается не более
pageSize+1 строк, лишняя строка определяет hasNextPage; возвращаются не более
pageSize. Допустимая страница за набором пуста, COUNT не обязателен.

Порядки:

- feed: first_published_at/id DESC; popular: like_count/first_published_at/id DESC;
- workspace: updated_at/id DESC; taxonomy: name/id ASC при collation C;
- roots/replies: created_at/id ASC; moderation: created_at/id DESC.

Категории фильтруются ANY через EXISTS; теги — ALL через подсчёт совпавших
уникальных joins, равный числу запрошенных ID, либо эквивалентные EXISTS.
Пустой фильтр не ограничивает результат. До выполнения фильтра проверяются
существование и отсутствие повторов: максимум 5 категорий/20 тегов по R-06.
Неизвестный ID — 400; известные фильтры без совпадений — пустая страница.

Feed получает карточки без Markdown одним ограниченным запросом, включая
счётчики и correlated EXISTS личного лайка. Ещё два batch-запроса получают
категории/теги для ID страницы; валидация фильтров добавляет максимум два batch
запроса. Максимум пять data queries независимо от числа карточек; фиксированные
auth/bootstrap обращения учитываются отдельно. ReadModels координирует разрешённые
контракты чтения модулей без циклической зависимости Publishing ↔ Engagement.
Изменение набора между страницами может сдвинуть offset; snapshot каталога не
обещается. На неизменном наборе уникальные критерии порядка исключают пропуски
и повторы. Персонализированные DTO не попадают в общий публичный cache.

## 8. Проверки модели при реализации

Миграции проверяются на пустом PostgreSQL 18 и при upgrade предыдущей схемы,
включая SQL ограничений, индексов, прав runtime/operator и риск блокировок.
Интеграционные тесты используют реальный PostgreSQL; unit-тесты доменных правил
не требуют БД/сети. Минимальные проверки целостности:

- конкурентный bootstrap создаёт одну LocalUser без повышенных назначений;
  Operator grant/revoke и аудит атомарны, Reader не отзывается;
- одинаковый slug создаёт только одну публикацию; tombstone не освобождает slug;
  stale version не меняет контент/состояние/назначения;
- удаление материала снимает joins, не раскрывает взаимодействия; назначение
  одновременно с удалением справочника не оставляет сирот;
- закрытие/удаление одновременно с комментарием/лайком/просмотром имеет допустимый
  последовательный результат и не оставляет публичного взаимодействия закрытого родителя;
- граница depth=5, другой материал/скрытый родитель, hide/delete/restore предков,
  счётчики Visible-потомков и отсутствие автора/текста в заглушках;
- 100 конкурентных лайков одной пары, смешанные реакции разных пользователей,
  rollback между source/aggregate и неотрицательность;
- 100 открытий одной пары, неперемещаемое окно, T+24h включительно, разные
  личности/реплики, очистка одновременно с регистрацией и сохранение агрегата;
- точные лимиты Unicode/UTF-8, непустая публикация, page overflow/пустые дальние
  страницы, SQL/количество запросов/планы обеих лент и всех фильтров.

Время и порядок конкурентных операций контролируются clock seam, барьерами и
отдельными соединениями; ожидание реальных суток не используется. Нагрузочный
стенд и критерии производительности определены в R-06; этот документ не
утверждает, что они уже выполнены.
