# Спецификация интеграции приложения с Identity

**Версия документа:** 1.0.

**Контракт:** Identity 1.1.0, REST API `/api/v1`.

**Сверено с исходниками:** 2026-10-24, commit `43dabc6`.

**Адресат:** агент, разрабатывающий сервис или приложение — потребитель Identity.

Документ самодостаточен: скопируй его в репозиторий потребителя и используй как
требования к интеграции. Доступ к исходникам Identity и установка agent skill для
этого не обязательны. Значения конфигурации конкретного окружения предоставляет
владелец окружения; примеры ниже не описывают работающую установку.

## 1. Главная инструкция агенту

Подключи существующий самостоятельный сервис **Identity** через HTTP для учётных
записей и аутентификации пользователей. Сначала изучи инструкции, стек, текущую
авторизацию, модель пользователей и конфигурацию приложения-потребителя. Следуй
архитектуре потребителя; ему не требуется .NET или архитектура репозитория Identity.

Реализуй только согласованные сценарии. Если задача — защищённый API, достаточно
проверки access JWT и локальной авторизации; не добавляй формы входа и хранилище
refresh tokens без необходимости. Для браузерного приложения используй BFF,
для native — защищённое хранилище ОС. Не заменяй уже работающего провайдера входа
и не мигрируй существующих пользователей без отдельного задания.

Обязательные границы:

- **У каждого проекта собственный экземпляр Identity и отдельная БД пользователей.
  Multitenancy и общий каталог аккаунтов между проектами не планируются.**
- Identity управляет паролями, подтверждением email, токенами, глобальным статусом
  учётной записи и её сессиями. Не дублируй эти механизмы в потребителе.
- Бизнес-роли, разрешения, подписки, данные продукта и доступ к нему
  принадлежат потребителю. Не добавляй их в Identity и не ожидай их в JWT.
- Используй HTTP API и публичные JWKS. Не подключай БД Identity, его внутренние
  проекты, password hashes, приватные ключи, SMTP или административные секреты.
- Identity использует собственный REST token protocol. Это **не OAuth2/OIDC/SSO**:
  нет discovery, authorization code/PKCE, `client_credentials`, `client_secret`,
  introspection или стандартного федеративного входа. Не выдумывай эти endpoints
  и не настраивай OIDC `Authority`.
- Административная Identity Console и её cookie не являются входом пользователей
  приложения. Не выдавай приложению административные права ради интеграции.
- Не выдумывай production URL, настроенного клиента, секреты или успешную проверку
  подключения. Отсутствующие значения оставляй явными обязательными настройками.

Если необходимая возможность отсутствует, опиши несовместимость. Изменение протокола
Identity — отдельная задача, а не скрытая часть реализации потребителя.

## 2. Входные параметры и границы окружения

До подключения реального окружения установи следующие значения. Если информация
уже есть в конфигурации или задании, используй её. Запрашивай только недостающие
решения, которые блокируют работу; независимые части выполняй с явными параметрами.

| Параметр | Значение и назначение |
| --- | --- |
| Тип потребителя | Браузер с BFF, native или API, проверяющий Bearer |
| API base URL | Доверенный адрес Identity без `/api/v1`, например `https://identity.example` |
| Issuer | Точное ожидаемое значение JWT `iss`; задаётся оператором Identity |
| Audience | Аудитория именно защищаемого API, согласованная с оператором |
| ClientId | Включённый публичный идентификатор из `Identity:Clients`, для login/register |
| JWKS URL | Фиксированный доверенный URL `/.well-known/jwks.json` конкретной установки |
| Экземпляр проекта | Собственный Identity и отдельная БД этого проекта; решение об изоляции уже принято |
| Сценарии | Только проверка JWT либо также login, регистрация, профиль, пароли, сессии |
| Email-страницы | Реальные адреса verify/reset/activation и фиксированные email templates |
| BFF session storage | Существующее защищённое серверное хранилище и координация между репликами |
| Окружение | Development/test/production, отдельные issuer/audience/ключи и тестовые данные |

API base URL, issuer, audience и clientId — разные понятия. Не вычисляй issuer из
адреса прокси и не подставляй clientId вместо audience. В локальном Compose из
Identity API доступен по `http://localhost:5080`, issuer по умолчанию равен
`https://identity.localhost`; клиенты `native` → `identity-native` и `backend` →
`identity-backend`. Это локальные примеры, не production-настройки и не клиенты,
которые гарантированно включены на иной установке.

`clientId` публичен и выбирает аудиторию. Он не аутентифицирует приложение,
не ограничивает пользователя одним продуктом и не является tenant или членством.
На refresh clientId/audience изменить нельзя. Каждый login выдаёт JWT с одной
аудиторией; не отключай audience validation ради вызова другого API.

Повторно используется код/образ Identity; каталог пользователей между проектами
не разделяется. Для каждого проекта предусмотрены собственные экземпляр, БД,
уникальный issuer, JWT key ring и отдельные ключи шифрования/сессий. Не подключай
новый проект к Identity другого проекта. Совпадение email не означает общий аккаунт
и не разрешает связывать пользователей разных проектов.

Внутри проекта допустимы несколько клиентов одного экземпляра, например BFF и
native: это способы доступа к одному продукту. Право работать с продуктом проверяет
потребитель. Logout-all, пароль, профиль и деактивация относятся к учётной записи
этого проекта и его клиентам; другие проекты используют независимые аккаунты.

Не добавляй tenantId, выбор экземпляра/issuer из пользовательского запроса,
общую межпроектную БД пользователей, межпроектный SSO или маршрутизацию по tenants.
Потребитель доверяет своему фиксированному экземпляру; настройки разных окружений
проекта также разделены. Отдельная БД может работать в общем PostgreSQL-кластере:
требование — изоляция данных и доступа, а не обязательный отдельный сервер БД.

## 3. Шаблон конфигурации

Названия ниже — настройки **потребителя**, а не новые параметры Identity.
Адаптируй их к стеку проекта. Все значения примера несекретны и требуют замены.

```json
{
  "IdentityIntegration": {
    "ApiBaseUrl": "https://identity.example",
    "Issuer": "https://identity.example",
    "Audience": "consumer-api",
    "ClientId": "consumer-bff",
    "JwksUrl": "https://identity.example/.well-known/jwks.json",
    "ClockSkewSeconds": 30,
    "HttpTimeoutSeconds": 5,
    "JwksCacheSeconds": 300
  }
}
```

На стороне Identity оператор добавляет включённый клиент в существующую
конфигурацию, сохраняя другие записи:

```json
{
  "Identity": {
    "Clients": [
      { "ClientId": "consumer-bff", "Audience": "consumer-api", "Enabled": true }
    ]
  }
}
```

Это фрагмент конфигурации сервера, не HTTP-запрос регистрации клиента. Его изменение
и применение к реальной установке требуют отдельного разрешения владельца.
Режимы `Registration:Enabled`, `PasswordReset:Enabled`, `Invitations:Enabled`,
`Jwt:Enabled` и почтовая доставка также определяются оператором.

В production проверяй обязательные настройки при запуске, требуй HTTPS для API/JWKS
и не допускай резервного перехода на dev issuer или sample audience. В dev HTTP
допустим только для явно настроенного локального стенда. Число 5 секунд — пример
ограниченного HTTP timeout, а не гарантия времени ответа login с password hashing.
Секреты BFF-хранилища и cookie protection задаются средствами окружения, не Git.
Значения примеров замени настройками экземпляра конкретного проекта; не копируй
рабочие issuer/key rings/БД другого проекта для совместного использования.

## 4. Архитектура потребителя

### 4.1. Браузерное приложение

```text
Browser -- cookie + CSRF --> собственный backend/BFF -- HTTPS JSON --> Identity
                                      |
                                      +-- Bearer access JWT --> защищённый API

Защищённый API -- кэшируемые публичные JWKS --> Identity
```

Браузер обращается к своему BFF на одном origin. BFF хранит пару access/refresh
на сервере и добавляет access token при вызове нужного API. Ответы BFF браузеру
содержат только безопасную проекцию пользователя и состояние локальной сессии.

Требования к BFF:

- Cookie содержит непрозрачный идентификатор локальной сессии; `Secure`, `HttpOnly`,
  host-only, подходящий `SameSite` и ограниченный срок. При использовании префикса
  `__Host-` соблюдай его требования: `Path=/`, без `Domain`, с `Secure`.
- Меняй идентификатор сессии после login. Не используй cookie Identity Console.
- Храни токены в устойчивом защищённом серверном session store, шифруй при хранении
  проверенными средствами с ключами отдельно от данных/бэкапов. Только память
  процесса не обеспечивает восстановление после restart и работу нескольких BFF.
- Access/refresh tokens не должны попадать в browser JSON, localStorage,
  sessionStorage, IndexedDB, читаемые JavaScript cookies или клиентские кеши.
- Защищай небезопасные cookie-запросы от CSRF, включая login/logout, проверяй origin
  по политике приложения. Один SameSite не заменяет весь механизм CSRF.
  Admin CSRF endpoints Identity не защищают BFF потребителя.
- Срок/активность BFF-cookie не доказывают активность сессии Identity. Учитывай
  expiry, отказ refresh, отзыв сессии и выбранную политику повторной проверки.
- Очищай защищённые клиентские данные после logout и подтверждённой утраты сессии.
  `403` на бизнес-операции не должен разлогинивать пользователя.

Серверные HTTP-вызовы BFF не требуют CORS Identity. Не включай разрешающий CORS
ради обхода BFF. Не проксируй настраиваемый пользователем URL и не отправляй Bearer
на произвольный host; отдельно проверь поведение HTTP-клиента при redirect.

### 4.2. Native и API

Native может вызывать REST token API напрямую. Refresh token хранится только в
защищённом хранилище ОС; access token — по возможности в памяти. Если несколько
окон/процессов делят одну сессию, они обязаны координировать refresh.

API, получающий пользовательский Bearer, проверяет JWT локально по разделу 6.
Ему не нужны refresh token, пароль или приватный ключ Identity. Если нужны
фоновые вызовы от имени сервиса, согласуй отдельный механизм: Identity не
предоставляет машинный grant. Не создавай для этого постоянный admin/password.

## 5. Пользователь и права в БД потребителя

Стабильная внешняя ссылка — **проверенные `issuer + sub`**. `sub` — UUID
пользователя Identity. `sid` — UUID конкретной сессии, не пользователь.

Рекомендуемая минимальная модель связи; реальные названия соответствуют проекту:

```text
app_users
  id                 локальный PK
  identity_issuer    точный доверенный issuer
  identity_subject   UUID из проверенного sub
  ...                собственные данные/статус/права приложения

UNIQUE(identity_issuer, identity_subject)
```

Эта пара фиксирует источник внешней личности, не добавляет multitenancy.
В одном окружении приложения принимается только его настроенный issuer.

Создавай/находи связь идемпотентно после проверенной аутентификации, учитывай гонку
первого входа ограничением уникальности в БД. Если продукт не допускает свободный
вход, создание связи не выдаёт членство или разрешения автоматически.

Не используй email как постоянный ключ, не связывай существующие аккаунты только
по совпадению email. Для миграции/объединения нужна отдельная проверка владения.
Не доверяй `userId`, email или ролям из browser JSON как доказательству личности.
В запросах данных выводи владельца из проверенного principal и локальной связи.

Канонические email/displayName хранятся в Identity; локальный кеш — явная проекция
с выбранным сроком актуальности. Профиль текущего пользователя запрашивается через
`GET /api/v1/users/me` с его access token. Обычного API поиска любых пользователей,
webhooks изменения профиля и потока синхронизации пользователей нет.

«Удалить пользователя из продукта» и «деактивировать учётную запись Identity»
— разные действия. Реализуй закрытие членства в продукте локально, если задача
не требует деактивации всего аккаунта проекта. Не обещай удаление PII через deactivate.

## 6. Проверка access JWT и JWKS

Используй стандартную JWT-библиотеку своего стека. Просто декодировать JWT
недостаточно. До доступа к данным проверь:

1. Подписанный JWT с разрешённым **RS256**, корректной подписью и известным `kid`.
   Отклоняй `alg=none`, подмену алгоритма и неподходящие ключи.
2. Точное совпадение `iss` и своей `aud` с доверенной конфигурацией; не принимай
   все аудитории Identity. Не ослабляй сравнение trailing slash без основания.
3. Обязательные `exp`, `nbf`, `iat`, их корректные типы и временные границы;
   clock skew не более 30 секунд. Часы серверов должны быть синхронизированы.
4. `token_use=access`; единственные корректные `sub` и `sid` как UUID,
   `client_id` и `jti`. Не принимай противоречивые/повторяющиеся identity claims.
   Дополнительный allowlist client_id может сужать доступ, но не заменяет audience
   validation или права продукта: clientId остаётся публичным селектором.
5. Собственные ограничения продукта: локальный статус, членство, права и владелец
   ресурса. Успешная JWT-проверка сама по себе не разрешает любую бизнес-операцию.

Выдаваемые claims: `sub`, `iss`, `aud`, `jti`, `sid`, `client_id`, `iat`, `nbf`,
`exp`, `token_use=access`. В текущей реализации `jti` — GUID в формате `N`.
Email и бизнес-роли не обещаны. Текущий JOSE `typ` — `JWT`; не требуй выдуманный
`at+jwt`. В .NET задай `MapInboundClaims=false`, читай `sub`/`sid` явно и не задавай
OIDC `Authority`/discovery metadata. Настрой verifier на публичный JWKS вручную.

JWKS возвращается по `GET /.well-known/jwks.json`, с `Cache-Control: public,
max-age=300`. Формат: объект `keys` с публичными RSA JWK (`kty`, `use`, `alg`,
`kid`, `n`, `e`). Приватных компонентов нет. Требования к загрузчику:

- Только фиксированный доверенный URL из конфигурации, HTTPS в production;
  не следовать `jku`/`x5u` из предъявленного токена и не подгружать случайные ключи.
- Кешировать ключи, иметь ограниченный timeout и согласованное обновление;
  не делать HTTP-запрос на каждую проверку access token.
- На неизвестный `kid` допустимо одно ограниченное обновление с объединением
  параллельных запросов и защитой от частых загрузок. Если ключ не найден — отказ.
- Поддержать ротацию: оператор Identity публикует старые public keys до истечения
  ранее выданных токенов. Потребитель должен получать новый набор без вечного
  кеша и повторного развёртывания с вшитым ключом.
- Описать поведение при недоступном JWKS: известные ключи — только в пределах
  явно выбранной политики кеша; без пригодного ключа доступ не предоставляется.
  Сетевой сбой не разрешает отключить подпись/issuer/audience validation.

Identity на своих защищённых endpoints дополнительно проверяет активность
пользователя/сессии по БД. Сторонний API с локальной JWT-проверкой этого не делает:
после logout, блокировки, смены пароля или деактивации старый JWT может проходить
до `exp + clock skew` (по умолчанию до примерно 15 минут + 30 секунд).

Не обещай мгновенный глобальный logout. Если продукту нужна более строгая гарантия,
согласуй серверную повторную проверку через `/api/v1/users/me`, её период, latency,
кеш и отказ при недоступности Identity либо собственную блокировку продукта.
Это существующий endpoint профиля с проверкой сессии, не introspection protocol.
Не добавляй непредусмотренные callbacks или endpoints отзыва.

## 7. HTTP-контракты Identity

Запросы JSON — `Content-Type: application/json`, имена полей `camelCase`.
Bearer означает `Authorization: Bearer <accessToken>`. Таблица описывает Identity,
а маршруты собственного BFF выбираются по соглашениям потребителя. На публичных
операциях Identity Bearer не требуется; cookie-защита BFF всё равно требует CSRF.

| Метод | Путь | Доступ | JSON body | Успех |
| --- | --- | --- | --- | --- |
| POST | `/api/v1/auth/register` | Public | `{email,password,displayName?,clientId}` | `202` generic message |
| POST | `/api/v1/auth/email/verification-request` | Public | `{email}` | `202` generic message |
| POST | `/api/v1/auth/email/verify` | Public | `{token}` | `204`, без body |
| POST | `/api/v1/auth/login` | Public | `{email,password,clientId}` | `200`, token pair |
| POST | `/api/v1/auth/refresh` | Public | `{refreshToken}` | `200`, новая token pair |
| POST | `/api/v1/auth/logout` | Public | `{refreshToken}` | `204`, без body |
| POST | `/api/v1/auth/logout-all` | Bearer | Нет body | `204`, без body |
| GET | `/api/v1/users/me` | Bearer | Нет body | `200`, profile |
| PATCH | `/api/v1/users/me` | Bearer | `{displayName}` | `200`, profile |
| POST | `/api/v1/users/me/deactivate` | Bearer | `{password}` | `204`, без body |
| POST | `/api/v1/auth/password/change` | Bearer | `{currentPassword,newPassword}` | `204`, без body |
| POST | `/api/v1/auth/password/forgot` | Public | `{email}` | `202` generic message |
| POST | `/api/v1/auth/password/reset` | Public | `{token,newPassword}` | `204`, без body |
| POST | `/api/v1/auth/invitations/accept` | Public, v1.1 | `{token,newPassword}` | `204`, без body |
| GET | `/api/v1/sessions` | Bearer | Нет body | `200`, session array |
| DELETE | `/api/v1/sessions/{id}` | Bearer | Нет body; `id` UUID | `204`, без body |
| GET | `/.well-known/jwks.json` | Public | Нет body | `200`, JWK Set |

`204` не содержит JSON: не пытайся десериализовать пустой body. Защищённые операции
относятся к текущему пользователю; общего `GET /users/{id}` для потребителя нет.

### 7.1. Token pair и профиль

Login и refresh возвращают один формат; значения ниже — placeholders:

```json
{
  "accessToken": "<signed-access-jwt>",
  "refreshToken": "<opaque-refresh-token>",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

`expiresIn` — срок access token в секундах, не refresh/session expiry. В ответе
нет userId/email/ролей, срока refresh и cookie пользовательского входа. Для
планирования refresh учитывай проверенный `exp` и `expiresIn`, а не постоянные
15 минут. Identity возвращает токены с `Cache-Control: no-store`.

Пример профиля; UUID, email и время иллюстративны:

```json
{
  "id": "72e11cbd-4a67-4f72-b1c2-af2439798ae7",
  "email": "user@example.com",
  "displayName": "Example User",
  "emailVerified": true,
  "status": "active",
  "createdAt": "2026-10-19T10:00:00Z"
}
```

`displayName` может быть `null`. PATCH требует именно поле `displayName`: строка
до 120 символов после trim, без control characters, либо `null` для очистки.
Пустая/whitespace строка, отсутствующее поле, неизвестные поля (`email`, `userId`)
дают `400`. Изменения email в текущем API нет.

`GET /sessions` возвращает массив, не объект пагинации. Поля: `id`, `clientId`,
`createdAt`, `lastUsedAt`, `absoluteExpiresAt`, nullable `userAgent`, `isCurrent`.
Только активные собственные сессии; `isCurrent` определяется по `sid`, не устройству.
`userAgent` — недоверенный текст: выводи безопасно. Список может включать разные
клиенты учётной записи внутри этого проекта; admin sessions имеют отдельный контракт.
Чужая/отсутствующая сессия при DELETE даёт одинаковый `404 session_not_found`.

### 7.2. Регистрация и жизненный цикл

- При включённой регистрации корректный запрос возвращает `202`, включая
  существующий email, без userId/tokens и без публичного `409 email exists`.
  Message: `If the request is eligible, a verification email will be sent.`
  Аналогичный ответ у verification-request. `202` не доказывает создание аккаунта
  или доставку письма. Не создавай локальную связь пользователя по такому ответу.
- Регистрация создаёт PendingVerification; login до подтверждения не проходит.
  Verify принимает одноразовый token в JSON и даёт `204`. Непригодный, истёкший,
  использованный token — одинаковый `400 invalid_verification_token`.
  Повторная отправка не гарантирует немедленную доставку; текущая реализация
  сохраняет старые verification tokens до истечения, но подтвердить аккаунт
  успешно можно только один раз.
- На register clientId проверяется по форме (1–100 символов, без control chars).
  Только login проверяет включение клиента в конфигурации. Не используй это
  различие как механизм ограничения регистрации/доступа в продукт.
- Login даёт generic `401 invalid_credentials` при неизвестном email, неверном
  пароле, неподтверждённом/заблокированном/деактивированном аккаунте, временной
  блокировке или неизвестном/выключенном клиенте. Не различай эти причины в UI
  через дополнительный поиск email. При выключенном JWT — `503 login_disabled`.
- Forgot возвращает generic `202` с message
  `If the request is eligible, a password reset email will be sent.` даже для
  неизвестного/непригодного аккаунта и при выключенном reset. Новая выдача reset
  делает предыдущие reset links недействительными. Reset даёт `204`; непригодный
  token — `400 invalid_password_reset_token`, без раскрытия причины.
- Change/reset/deactivate отзывают **все** сессии пользователя, включая текущую
  и административные. Успех — пустой `204`, новой пары и автоматического login нет.
  Заверши текущую локальную сессию потребителя. Для другого браузера/клиента
  применяются правила обнаружения отзыва из раздела 6.
- Deactivate требует текущий пароль, терминален для публичного API и сохраняет
  email/credentials/audit. Это не удаление данных и не выход из одного продукта.
- Logout-all действует на все клиенты учётной записи этого проекта и admin sessions.
  Удаление текущей сессии через DELETE также завершает её вход.
- Invitation acceptance — необязательный контракт v1.1 для аккаунта Invited,
  созданного администратором без пароля. `204` означает установку начального
  пароля/подтверждение email/Active, но не login и не выдачу роли. Непригодный token
  или выключенные invitations — `400 invalid_invitation_token`. Потребителю не
  нужны admin cookie/API для принятия ссылки; создание приглашений не входит
  в обычную интеграцию пользовательского входа.

Пароль для регистрации/нового пароля: 15–128 Unicode code points после NFKC,
не более 1024 UTF-8 bytes до нормализации и 512 после, локальный denylist.
Не обрезай пробелы, не меняй и не усекай пароль молча; не вводи обязательные классы
символов. UI-проверки — подсказки, backend остаётся источником решения. Для login
не применяй текущую политику нового пароля к уже существующему паролю.

Email ограничен 320 символами, без control characters. Identity применяет trim
и invariant-нормализацию регистра для сравнения, без специальных Gmail-правил.
Не используй собственное преобразование email для связывания внешних аккаунтов.

Типичные сроки: access 900 секунд, refresh до 7 дней, абсолютная сессия 30 дней,
verification 24 часа, reset 30 минут, invitation 72 часа. Настройки могут отличаться;
refresh не продлевает абсолютную сессию. Не выдумывай отсутствующие в DTO поля expiry.

## 8. Refresh, конкуренция и неопределённый результат

Refresh token непрозрачен; не разбирай его как JWT. На каждый успешный refresh
получается новая пара, старый refresh становится consumed. `sid`, clientId и
audience сохраняются. Дополнительные clientId/audience не меняют привязку сессии.

**Строгий replay:** предъявление consumed refresh отзывает всё семейство, включая
уже выданную замену. Grace window и безопасного повторного обмена старого токена
нет. Два конкурентных запроса могут получить `200` и `401`, после чего даже новая
пара победителя уже не позволяет refresh. Поэтому реализация обязана:

1. Координировать refresh по сессии Identity во всех запросах и репликах BFF;
   native — во всех процессах, разделяющих хранилище. Process-local mutex для
   нескольких реплик недостаточен. Все локальные ссылки на одну token pair
   должны использовать одну область координации.
2. Внутри координации заново читать последнюю версию пары. Если другой запрос
   уже обновил её, использовать новую пару без повторного обмена старого refresh.
3. Если refresh всё ещё нужен, вызвать endpoint один раз. Проверить ответ и
   атомарно сохранить **оба** новых токена, expiry и версию до освобождения
   координации. Не позволять запоздавшему запросу затереть новую пару.
4. Применять механизм, который исключает параллельный HTTP-обмен одним refresh,
   например устойчивую блокировку с корректным управлением временем владения.
   Один CAS при сохранении результата уже после двух HTTP-запросов не защищает
   от replay. Конкретное средство выбирай по существующей инфраструктуре.

При timeout/обрыве/отмене запроса результат может быть уже закоммичен в Identity.
При потере ответа или невозможности надёжно сохранить новую пару **не повторяй
старый refresh**, не включай для него общие HTTP retries. Заверши локальную сессию
и предложи новый login. Допустим ограниченный best-effort logout известного
семейства; его сетевой сбой не доказывает отзыв. Отмена запроса не отменяет commit.

`401 invalid_refresh_token` одинаков для unknown/expired/revoked token,
неактивной сессии/пользователя, lockout, выключенного клиента/JWT или изменённой
audience. Не пытайся лечить это циклом refresh. Не обновляй токены при каждом
`401`: отличай истечение access от неверной подписи/audience, отзыва и бизнес-ошибок.

После координированного refresh исходный бизнес-запрос можно повторить не более
одного раза и только когда это безопасно по его семантике. Не повторяй списание,
создание заказа или другую запись автоматически без гарантии, что она ещё не
выполнилась, либо согласованной идемпотентности.

Logout использует `{refreshToken}` и идемпотентен: unknown, malformed token,
already revoked дают тот же `204` (malformed JSON остаётся ошибкой). Известный
consumed/expired token также позволяет отозвать семейство. Logout не выдаёт токены.
Координируй logout с refresh: сначала закрой локальную сессию для новых операций,
не разрешай позднему refresh восстановить её. После logout удали cookie/серверное
состояние; при сетевой ошибке не объявляй удалённый отзыв подтверждённым и не
сохраняй вход активным только ради повторного запроса.

## 9. Email-ссылки и публичные страницы

Identity формирует ссылки по фиксированным серверным параметрам
`Email:VerificationUrlTemplate`, `Email:ResetPasswordUrlTemplate`,
`Email:InvitationUrlTemplate`. Клиент не задаёт произвольный redirect/return URL.
Templates общие для экземпляра: clientId не выбирает отдельный адрес/брендинг
продукта. У каждого проекта свои templates, ведущие на его реальные страницы
или Console его экземпляра Identity; согласуй безопасную навигацию после операции.

В Identity Console 1.1.0 поставляются `/account/activate` и
`/account/reset-password`, работающие без административного входа. Их доступность
получателю зависит от ingress/VPN конкретной установки. Готовой страницы
`/account/verify` нет. Для verification реализуй страницу потребителя и согласуй
с оператором, например:

```text
Email:VerificationUrlTemplate = https://consumer.example/account/verify#token={token}
```

Это пример серверной настройки, не принимаемый от браузера параметр регистрации.
Для reset можно использовать реальную страницу Console либо собственную страницу
потребителя с существующим JSON API. Не считай старые dev-ссылки `/verify` и `/reset`
из `.env.example` готовыми страницами Identity.

На своей странице email-потока прочитай `#token=...` один раз и немедленно убери
fragment через `history.replaceState` до аналитики, диагностик и других эффектов.
Храни token только в памяти страницы, передай в JSON body соответствующего POST,
после завершения удали. Не помещай его в query, persistent storage, router state,
кеш запросов, логи и скриншоты. Установи `Referrer-Policy: no-referrer` и не
подключай отслеживание на страницах с секретами. После успеха нужен обычный login.

## 10. Ошибки, ограничения и эксплуатация адаптера

Ожидаемый формат — `application/problem+json`. Пример:

```json
{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 400,
  "code": "validation_failed",
  "traceId": "<correlation-id>",
  "errors": { "email": ["Enter a valid email address without control characters."] }
}
```

Учитывай HTTP status и `code`; не привязывай поведение к английскому `title`.
Обрабатывай пустой/non-JSON ответ, сетевой timeout, отмену и недоступность edge.
Не показывай пользователю произвольный сырой body или exception text.

| Status / code | Поведение потребителя |
| --- | --- |
| `400 validation_failed` | Известные безопасные ошибки полей; ввод пользователя не теряется без причины |
| `400 invalid_request`, `413 request_too_large` | Ошибка формы/размера запроса, без повторов с теми же данными |
| `400 invalid_verification_token`, `invalid_password_reset_token`, `invalid_invitation_token` | Ссылка непригодна; одинаковое сообщение без детализации причины |
| `401 invalid_credentials` | Нейтральное сообщение об отказе login/current password, без проверки существования email |
| `401 invalid_refresh_token`, `unauthorized` | Учитывать контекст; завершить непригодную сессию, без refresh loop |
| `403 forbidden` | Недостаточно прав, не автоматический logout |
| `404 session_not_found` | Сессия недоступна; одинаково для чужой/отсутствующей |
| `409 concurrency_conflict` | Перечитать состояние; запись автоматически не повторять |
| `429 rate_limited` | Уважать `Retry-After`, ограничить UI-повторы; не переигрывать refresh вслепую |
| `503 registration_disabled`, `login_disabled` | Функция недоступна, без выдуманного успешного результата |
| Остальные `5xx`/network | Безопасное сообщение о недоступности; результат записи может быть неопределённым |

Auth/profile body ограничен 16 KiB; поля имеют отдельную валидацию. Есть IP/account
rate limits и временная блокировка login. За BFF запросы могут иметь общий исходящий
IP: согласуй лимиты с оператором и добавь защиту собственного BFF. Не подделывай
`X-Forwarded-For`; forwarding доверяется только по явно настроенной топологии.

Не логируй password, access/refresh/one-time token, Authorization/Cookie/Set-Cookie,
email URL с token или полный HTTP body авторизации. Применяй redaction также к
APM, HTTP-client diagnostics, exception telemetry, тестовым отчётам и browser traces.
Для диагностики используй status, безопасный code и traceId/`X-Correlation-ID`;
не добавляй email/tokens в metric labels.

`GET /health/live` проверяет живость процесса, `/health/ready` — подключение к БД,
но не доставку email и не полную готовность login. Readiness — внутренний endpoint,
не открывай его наружу ради интеграции. `/openapi/v1.json` доступен в Development,
в Production его отсутствие ожидаемо. Не делай production-зависимость от OpenAPI.

## 11. Порядок реализации в другом репозитории

1. Установи тип потребителя, сценарии и параметры раздела 2. Зафиксируй границу
   отдельного экземпляра проекта, локальные права и допустимую задержку отзыва access JWT.
2. Добавь валидируемую конфигурацию с несекретным примером, стандартную JWT/JWKS
   проверку и небольшой типизированный HTTP-адаптер только нужных операций.
3. Создай уникальную связь `issuer + sub` с локальным пользователем и проверки
   прав/владения, сохраняя уже существующие соглашения проекта.
4. Для браузерного login реализуй BFF session/CSRF/защищённое хранилище и
   координацию refresh/logout; для native — соответствующие механизмы ОС.
5. Реализуй согласованные формы/email-сценарии и безопасные ошибки. Объясни
   пользователю глобальные последствия logout-all/пароля/деактивации.
6. Проверь адаптер и сквозные сценарии по разделу 12 в отдельном окружении.
   Обнови README/config sample/runbook потребителя; не выполняй внешний deploy,
   миграцию реальных пользователей и изменение Identity без разрешения.

Не создавай универсальный auth framework или SDK без потребности. Предпочитай
существующие HTTP/session/crypto средства проекта и явные контракты.

## 12. Проверки и критерии приёмки

Проверяй только реализуемые сценарии; для API-only не требуются формы/BFF.
Unit/contract tests с fixtures полезны для ошибок, но не доказывают реальную
интеграцию. Сквозные проверки выполняй с настоящим Identity в изолированном
Development/test окружении и одноразовыми данными, не с production-аккаунтами.
Если проверяешь хранение/конкуренцию внутри Identity, используй настоящий
PostgreSQL; EF InMemory не подтверждает его корректность.

| Область | Обязательное доказательство для соответствующего сценария |
| --- | --- |
| Изоляция проекта | Фиксированный собственный issuer; JWT другого проекта отклонён; нет tenant-маршрутизации и зависимости от его каталога пользователей |
| JWT | Валидный token проходит; tampered/expired/future nbf, неверные issuer/audience/alg/token_use и обязательные claims отклоняются |
| JWKS | Кеш, новый kid/плановая ротация, неизвестный kid и недоступный сервер не приводят к обходу проверки или шторму загрузок |
| Локальные права | Анонимный запрос отклонён; чужие ресурсы и отсутствующее членство недоступны при валидном JWT |
| Пользователь | Два конкурентных первых входа создают одну локальную связь; email/userId из запроса не подменяют владельца |
| Register/verify | Generic 202 для нового/существующего email; до verify login отказан; после письма/verify вход успешен; replay verification отклонён |
| Login/profile | Успех, generic отказ, получение своего профиля и согласованный PATCH displayName |
| Refresh | Последовательная ротация; одновременные запросы потребителя делают один обмен и сохраняют новую пару без потери |
| Replay | Отдельный негативный сценарий: прямой повтор старого refresh отзывает всё семейство, новая замена тоже не обновляется |
| Неопределённый refresh | Потеря ответа/сбой сохранения/отмена завершают локальный вход без повторного обмена старого refresh |
| Logout | Cookie/локальный store/клиентские данные очищены, refresh отозван; гонка с refresh не восстанавливает вход; network failure не выдаётся за подтверждённый отзыв |
| Password/reset/deactivate | One-time token/replay/policy; после успеха нет auto-login, текущая сессия завершается; глобальные последствия отражены |
| BFF | Реальные cookie attributes, CSRF на login/logout/записи, session fixation protection и координация между репликами |
| Privacy | В browser JSON/storage/cache/URL и логах/трейсах/артефактах нет секретов; fragment сразу очищается |
| Ошибки | 204/202/400/401/403/429/503, non-JSON/timeout; нет enumeration, refresh loops и небезопасного replay бизнес-записей |

Временные реальные токены для негативных тестов формируй в памяти тестового стенда,
не сохраняй подписанные JWT/пароли в репозиторий и не печатай их в отчёты. Не требуется запускать
весь test suite Identity при изменении только документации потребителя.

В итоговом отчёте агента укажи форму интеграции, изменённые файлы/миграции,
обязательные настройки оператора, точные выполненные команды и результаты,
невыполненные live-проверки, политику refresh/JWKS/отзыва и остаточные ограничения.
Mock-only проверки не называй успешным end-to-end подключением.

## 13. Совместимость и сверка источников

Это снимок доставленного контракта Identity 1.1.0, а не обещание версии или
включённых функций конкретной установки. При наличии исходников сверяй:

- `Identity_Codex_Spec.md` — базовые требования; `Identity_Admin_Codex_Addendum.md`
  и `Identity_Admin_Codex_Addendum_v1.2.md` расширяют административный scope v1.1.
- `src/Identity.Api/Controllers/{Auth,Users,Sessions,Discovery}Controller.cs`,
  `src/Identity.Api/Contracts/`, `src/Identity.Application/Common/TokenPairResult.cs`
  — маршруты/DTO; profile/session DTO находятся в соответствующих query-файлах.
- `src/Identity.Infrastructure/Security/JwtTokenService.cs`, `JwtOptions.cs`,
  `src/Identity.Api/Configuration/JwtAuthentication.cs` — claims/настройки/проверки.
- `docs/api.md`, `docs/console-production.md`, `src/Identity.Admin.Web/src/app/routes.tsx`
  — примеры, эксплуатация и реально поставляемые страницы.

Исторические stage-заметки могут описывать более раннее состояние. В частности,
базовая спецификация v1.0 исключает admin/frontend; они добавлены дополнением v1.1,
но обычный пользовательский SPA-вход не появился. Некоторые старые заметки
