# Исходные ограничения и зависимости Blog Engine MVP

Дата: 2026-10-24. Источник: запрос владельца проекта и приложенная спецификация Identity.
Этот файл сохраняет заданные технические ограничения для `$speckit-plan`;
продуктовые сценарии и проверяемые правила находятся в [spec.md](../spec.md).

## Задано владельцем

- Backend: ASP.NET Core Web API (.NET); PostgreSQL; только backend, без frontend.
- REST API с OpenAPI/Swagger, публичные операции чтения и счётчиков,
  защищённые операции управления публикациями, комментариями и лайками.
- Единая валидация, единообразные ошибки, пагинация растущих коллекций.
- Контент публикаций — Markdown.
- Проверка JWT внешнего существующего Identity Service; собственные регистрация,
  вход, хранение паролей и выдача токенов исключены.
- Эффективное получение ленты без N+1; корректные конкурентные счётчики,
  уникальные лайки, защита повторных просмотров, автоматизированные проверки бизнес-логики.
- Повторное использование в разных проектах и расширение без существенной переработки.
- Не добавлять микросервисы, брокеры и дополнительную инфраструктуру без
  доказанной необходимости. Не расширять MVP несогласованными возможностями.

## Применимые инженерные правила

Обязательна [конституция проекта](../../../.specify/memory/constitution.md), версия 1.0.0:
EF Core/Npgsql и миграции, ограничения целостности в PostgreSQL, ограниченные
детерминированные выборки, защита от потерянных обновлений, ProblemDetails,
тесты с настоящим PostgreSQL, безопасные логи и конфигурация, эксплуатационная готовность.
Версии инструментов, архитектура, схема, маршруты и формат передачи версии
сущности выбираются на этапе планирования.

## Граница внешней аутентификации

Нормативный источник: [Identity_Integration_Spec.md](Identity_Integration_Spec.md),
версия документа 1.0, заявленный контракт Identity 1.1.0, сверка источника
2026-10-24 с commit `43dabc6`. Это приложенный владельцем снимок контракта,
а не результат проверки работающей установки.

Дополнительно при подготовке спецификации прочитаны локальные `JwtTokenService.cs`,
`JwtAuthentication.cs` и `DiscoveryController.cs` репозитория Identity на commit
`43dabc6`: подтверждены состав выдаваемых claims, RS256 и публичный JWKS с max-age=300.
Это чтение исходников, не проверка сетевого подключения.

- Форма интеграции: только Bearer API. Login/register/refresh/logout,
  BFF, cookie-сессии и email-сценарии не реализуются движком.
- Каждый проект использует свой фиксированный экземпляр Identity и изолированную
  БД аккаунтов; общие каталоги, multitenancy и межпроектный SSO исключены.
- JWT: RS256, доверенный `kid`, точные `iss` и `aud`, обязательные `exp`, `nbf`, `iat`,
  `token_use=access`, единственные корректные UUID `sub`/`sid`, `client_id`, `jti`.
  `MapInboundClaims=false`; clock skew не более 30 секунд.
- Identity не является OIDC: не использовать `Authority`, discovery,
  introspection или выдуманные endpoints. `clientId` не является ролью/tenant.
- Публичный JWKS берётся только с фиксированного настроенного адреса;
  HTTPS обязателен в production; `jku`/`x5u` токена не выбирают источник ключей.
- Базовая политика MVP: пригодный кеш ключей до 300 секунд, ограниченное
  объединённое обновление при неизвестном `kid`; без пригодного ключа проверка
  закрывается отказом. Ротация поддерживается без вшитого постоянного ключа.
  Предел частоты обновлений и timeout определяются планом и проверяются тестами.
- Отзыв Identity обнаруживается не мгновенно: локально проверяемый access JWT
  может действовать до `exp + skew`; 900 секунд — типичный срок из источника,
  а не гарантированная настройка окружения. Повторная проверка `/users/me` не входит в MVP.
- Пользователь и локальные роли принадлежат Blog Engine; ключ связи — проверенные
  `issuer + sub`. Ни роли, ни email/displayName не обещаны в токене.
- Обязательные настройки оператора: точный issuer, audience и JWKS URL данного
  окружения; не использовать иллюстративные значения как рабочую конфигурацию.
- Не обращаться к БД Identity и его административному API; не хранить
  credentials, приватные ключи или refresh tokens. Секреты не попадают в артефакты.

## Проверки на следующих этапах

Автоматические проверки API используют изолированные тестовые ключи/ответы,
проверяют отрицательные JWT/JWKS-сценарии и не зависят от доступности живого Identity.
Перед заявлением о реальном end-to-end подключении требуется отдельный проверенный
test-экземпляр Identity с одноразовыми данными и предоставленной конфигурацией.
Сейчас выполняется только спецификация; подключение и live-проверки не выполнялись.
