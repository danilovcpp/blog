# Backend Requirements Quality Checklist: Файлы и аватары пользователей

**Purpose**: Оценить полноту, ясность, согласованность и измеримость серверных требований к файлам и аватарам перед реализацией.
**Created**: 2026-11-11
**Feature**: [spec.md](../spec.md)
**Focus**: Доступ и приватность; квоты, жизненный цикл и восстановление; согласованность потребительских и эксплуатационных контрактов.
**Depth**: Standard — общий обзор, вариант A выбран пользователем.
**Actor / Timing**: Ревьюер требований перед реализацией, после подготовки технического плана.

**Note**: Этот пользовательский чек-лист создан командой `$speckit-checklist` по спецификации, [плану](../plan.md), [HTTP-контракту](../contracts/http-api.md), [эксплуатационному контракту](../contracts/operations.md) и [конституции](../../../.specify/memory/constitution.md). `tasks.md` на момент создания отсутствует.
**Review Ownership**: Чек-лист принадлежит ревьюеру требований. Отметка `[x]` ставится только после его оценки соответствующего критерия качества требований.
**Marker Semantics**: `[x]` означает одобрение качества требований, а не завершение реализации или успешную приёмку работающей функции. При генерации все пункты оставлены `[ ]`.

## Полнота требований

- [ ] CHK001 Определена ли полная матрица прав гостя, Reader, владельца, другого Author, Moderator и Admin для каждого назначения файла, включая права после отзыва Author и запрет изменения чужого аватара? [Completeness, Spec §FR-001, Spec §FR-002, Spec §FR-020, Spec §SC-002]
- [ ] CHK002 Описаны ли наблюдаемые состояния файла и попытки загрузки, допустимые переходы между ними и доступность результата для потребителя в каждом состоянии? [Completeness, Spec §FR-003, Spec §FR-009, Spec §FR-026, Spec §FR-027]
- [ ] CHK003 Полностью ли определены требования к обложке, иллюстрациям и вложениям: назначение файла, владение, количество связей и выбор между внешней и управляемой обложкой? [Completeness, Spec §FR-013, Spec §FR-014]
- [ ] CHK004 Заданы ли требования к аватару или его явному отсутствию для собственных данных пользователя и всех представлений авторства, включая обезличенные комментарии? [Completeness, Spec §FR-020, Spec §FR-023, Spec §SC-003]
- [ ] CHK005 Документирован ли полный набор различимых ошибок потребителя с устойчивыми причинами и допустимыми сведениями ответа для неверных данных, квоты, прав, занятости файла, конфликта и временного отказа? [Completeness, Spec §FR-031, Constitution §IV, HTTP contract §Новые стабильные ошибки]

## Ясность требований

- [ ] CHK006 Однозначно ли заданы единицы, включительность границ и источник измерения для лимитов 50/10/5 MiB, числа пикселей и длины стороны изображения? [Clarity, Spec §FR-004, Spec §FR-007]
- [ ] CHK007 Достаточно ли точно определены нормализация имени, подсчёт его длины и запрещённые символы, чтобы разные потребители одинаково трактовали допустимое исходное имя? [Clarity, Spec §FR-005]
- [ ] CHK008 Однозначно ли разделены занятый объём, активный резерв, доступный остаток и физически хранимые производные, включая момент изменения каждого показателя при удалении и замене аватара? [Clarity, Spec §FR-008, Spec §FR-029, HTTP contract §Библиотека, квота и закрытое содержимое]
- [ ] CHK009 Определены ли начало отсчёта, точная граница и условия применимости сроков «немедленно», 60 секунд, 5 минут и 24 часа, включая период недоступности зависимостей и уже разрешённую передачу? [Clarity, Spec §FR-017, Spec §FR-024, Spec §FR-027, Spec §FR-028]

## Согласованность требований

- [ ] CHK010 Согласованы ли требования к закрытому хранению исходников публикаций с правилами подготовки изображений и очистки, а отдельное правило удаления исходников аватаров явно отличено от них? [Consistency, Spec §FR-011, Spec §FR-021, Spec §FR-025, Spec §FR-028, Spec §A-006]
- [ ] CHK011 Согласован ли отзыв доступа через закрытую публикацию с сохранением доступа к тому же файлу через другие опубликованные материалы без раскрытия остальных связей? [Consistency, Spec §FR-015, Spec §FR-016, Spec §FR-017, Spec §A-005]
- [ ] CHK012 Согласованы ли запрет удаления используемого файла, снятие связей при удалении публикации и атомарность версии материала, включая операции Admin? [Consistency, Spec §FR-018, Spec §FR-019]
- [ ] CHK013 Согласованы ли правила сохранения прежнего контента и управляемых связей между спецификацией и контрактом, в том числе различия отсутствующего поля, явного сброса и прежнего адреса обложки? [Consistency, Spec §FR-014, Spec §FR-033, Plan §Contract and compatibility decisions, HTTP contract §Связи публикации и доступ читателей]

## Качество критериев приёмки

- [ ] CHK014 Прослеживается ли каждое FR-001–FR-033 до пользовательского сценария или измеримого результата SC-001–SC-008, включая негативные исходы и ограничения области функции? [Traceability, Spec §Functional Requirements, Spec §User Scenarios & Testing, Spec §Measurable Outcomes]
- [ ] CHK015 Достаточно ли определены контрольные наборы и критерии точного совпадения имён и байтов до и после перезапуска и очистки для вложений и закрытых исходников изображений? [Measurability, Spec §SC-001, Spec §FR-011, Spec §FR-012]
- [ ] CHK016 Задаёт ли SC-004 однозначные условия 100 одновременных операций на общую квоту, публикацию и аватар и наблюдаемые критерии отсутствия потерянных изменений, дубликатов текущего аватара и недействительных связей? [Measurability, Spec §SC-004, Spec §FR-008, Spec §FR-019, Spec §FR-022]
- [ ] CHK017 Определены ли для SC-002 все сочетания ролей, состояний загрузки и публикации и виды защищаемых сведений, чтобы критерий отсутствия неразрешённого раскрытия имел конечную область оценки? [Acceptance Criteria, Spec §SC-002, Spec §FR-015, Spec §FR-016]

## Покрытие сценариев

- [ ] CHK018 Полны ли требования к четырём самостоятельным основным сценариям: личной библиотеке, файлам публикации, собственному аватару и управлению местом, без зависимости от будущего подключения интерфейса? [Coverage, Spec §User Story 1, Spec §User Story 2, Spec §User Story 3, Spec §User Story 4, Spec §Scope and Boundaries]
- [ ] CHK019 Определены ли альтернативные сценарии существующего пользователя без локального профиля или аватара, старой публикации с внешней обложкой и владельца с отозванной ролью Author? [Coverage, Spec §Edge Cases, Spec §FR-001, Spec §FR-023, Spec §FR-033]
- [ ] CHK020 Полны ли требования к исключениям при обрыве передачи, переполнении или недоступности хранилища, потере ответа и отсутствии либо повреждении содержимого при готовых метаданных? [Coverage, Spec §Edge Cases, Spec §FR-009, Spec §FR-026, Spec §FR-030, Spec §SC-005]
- [ ] CHK021 Разделены ли требования к восстановлению временно неудачной попытки и к окончательному отклонению, отмене или истечению срока, включая сохранность прежнего аватара, отсутствие повторного расхода квоты и запрет восстановления удалённых данных? [Coverage, Spec §FR-022, Spec §FR-026, Spec §FR-027, Spec §FR-029, Spec §SC-005]

## Граничные случаи

- [ ] CHK022 Определены ли ожидаемые категории исходов для пустого файла, точного лимита, превышения на один байт, несовпадения заявленных и фактических данных, анимации, повреждения и подмены формата изображения? [Edge Case, Spec §Edge Cases, Spec §FR-004, Spec §FR-007, Spec §SC-004]
- [ ] CHK023 Описаны ли требования к итоговому состоянию и сохранению инвариантов при пересечении завершения, истечения и очистки загрузки, привязки и удаления файла, замены аватара и удаления его предшественника? [Edge Case, Spec §Edge Cases, Spec §FR-019, Spec §FR-022, Spec §FR-029]
- [ ] CHK024 Однозначно ли различены одинаковые имена независимых файлов и повторные связи одного файла, включая правила подсчёта лимитов связей в одной публикации и использования файла несколькими публикациями? [Edge Case, Spec §User Story 1, Spec §FR-003, Spec §FR-014, Spec §FR-015, Gap]
- [ ] CHK025 Достаточно ли определены требования к пустой и последней странице библиотеки, недопустимым параметрам, совпадающим временам создания и устойчивости порядка при изменении набора файлов? [Edge Case, Spec §FR-010, HTTP contract §Библиотека, квота и закрытое содержимое, Gap]

## Нефункциональные требования

- [ ] CHK028 Заданы ли требования к различению работоспособности процесса и готовности зависимостей, диагностике сбоев и отставания очистки, срокам предупреждений и исключению секретов или лишних личных данных из диагностики? [Non-Functional, Spec §FR-028, Spec §FR-030, Spec §FR-031, Constitution §VI, Operations contract §Health, logs и cleanup]

## Notes

- Все 36 пунктов созданы неотмеченными; оценка качества требований в эту команду не входит.
- Отмечайте `[x]` только после подтверждения критерия ревьюером; при пробеле, неоднозначности или конфликте оставляйте `[ ]` и добавляйте замечание рядом с пунктом.
- Ссылки `Spec §…` относятся к разделам и идентификаторам [spec.md](../spec.md); `Plan §…` — к [plan.md](../plan.md); `HTTP contract §…` — к [http-api.md](../contracts/http-api.md); `Operations contract §…` — к [operations.md](../contracts/operations.md); `References §…` — к [source-constraints.md](../references/source-constraints.md); `Constitution §…` — к [constitution.md](../../../.specify/memory/constitution.md).
- `[Gap]`, `[Ambiguity]`, `[Conflict]` и `[Assumption]` внутри тегов обозначают предмет оценки, а не уже вынесенное ревьюером заключение.
- `$speckit-implement` читает состояние чек-листов как условие перехода и не изменяет отметки.
- [requirements.md](requirements.md) имеет отдельный встроенный жизненный цикл `$speckit-specify` / `$speckit-clarify`; его прежние отметки не закрывают этот чек-лист.
- Подключение UI/BFF, дизайн прототипа и изменение внешней службы входа находятся за границами текущей функции. Отдельных дополнительных обязательных пунктов пользователь не задавал.
- Нумерация CHK001–CHK036 последовательна и служит для ссылок в ревью.
