# HTTP-контракт файлов и аватаров

Статус: проектный контракт Phase 1, не описание уже реализованного API.
Основание: [спецификация](../spec.md), [решения](../research.md),
[модель данных](../data-model.md). Машиночитаемое дополнение —
[openapi.yaml](openapi.yaml); эксплуатация — [operations.md](operations.md).

## Сборка нормативного контракта и переход потребителей

Базовый контракт — `specs/001-blog-engine-mvp/contracts/openapi.yaml`.
Он сохраняется историческим. Новый YAML — **feature delta**, а не замена
всего API: скопировать baseline, объединить `paths` по пути и HTTP-методу,
объединить все разделы components (включая responses и securitySchemes)
и целиком заменить одноимённые schemas из delta. До публикации итогового
самодостаточного документа переписать ссылки delta вида
`../../001-blog-engine-mvp/contracts/openapi.yaml#/components/...` в локальные
`#/components/...`. Нельзя отдавать файловые относительные ссылки в runtime
OpenAPI по `/openapi`: там они не указывают на исторический YAML репозитория.
Все прежние операции, security, headers и ошибки сохраняются, если здесь
нет явного изменения. Замена строгой схемы выполняется целиком: `allOf`
поверх прежнего `additionalProperties: false` не расширяет её.

До включения функции согласованно обновить описание API, DTO-потребителей
и проверки схем. Старые строгие схемы `Me`/`AuthorRef` не принимают новые поля;
изменение нельзя объявлять автоматически совместимым. Старый контент остаётся
валидным, новые поля записи необязательны. Runtime OpenAPI проверяется до
документального объединения, чтобы overlay не скрывал отсутствующие endpoints.
Production UI и подключение прототипа выполняются отдельным этапом.

## Общие правила

- Префикс `/api/v1`; UUID в формате D, UTC RFC 3339, JSON camelCase.
  Неизвестные JSON-поля отклоняются. Тела у GET/DELETE и команд complete отсутствуют.
- Bearer обязателен, кроме явно публичных download/avatars. Переданный неверный
  Bearer даёт отказ, а не переход к гостевому доступу. Владелец определяется
  исключительно из проверенного контекста.
- Все ответы этого расширения, включая binary и ошибки: `Cache-Control: no-store`.
  Общий кеш не используется, validators/304 не выдаются. `Range` игнорируется:
  успешный ответ содержит полный файл и статус 200, без `Accept-Ranges`.
- JSON-запросы сохраняют существующий предел 8 MiB. Только raw content PUT
  имеет отдельный лимит фактических байтов соответствующего назначения. Этот
  лимит определяется назначением загрузки и не зависит от `declaredSize`.
  Binary endpoints принимают соответствующий `Accept`; они не проходят
  JSON-буферизацию. Недопустимый Accept — 406 ProblemDetails.
- API возвращает ошибки как `application/problem+json` с `type`, `title`, `status`, `code`,
  `traceId`, при валидации `errors`. Никаких bucket/key/секретов или внутренних URL.
  Временный 503 содержит `Retry-After` как положительное целое число секунд;
  это рекомендуемая задержка повтора, не обещание восстановления к этому сроку.
- Чужой закрытый, отсутствующий, удалённый, неготовый и недоступный ресурс
  неразличимы: 404 `resource_not_found`. Проверка доступа предшествует версии
  и закрытым метаданным. Неподходящая роль для нового действия — 403 `forbidden`.

### Матрица доступа для приёмки SC-002

Гость, Reader, владелец, другой Author, Moderator и Admin проверяются для
каждой группы операций ниже. Роли складываются по существующим правилам.
Варианты владельца включают Author, Admin, Reader с собственным аватаром
и владельца обычного файла после отзыва Author. Неверный Bearer даёт 401.

| Операции и состояния | Разрешение |
|---|---|
| Новый init, PUT и complete для Attachment/PublicationImage | Author/Admin на своей загрузке. PUT и complete проверяют текущие роли. Чужой upload даёт 404 даже для Admin. |
| Новый init, PUT и complete для Avatar | Любой вошедший пользователь на своей загрузке. |
| Status, cancel, точный init replay и исторический Completed replay | Только владелец, включая владельца после отзыва роли. Проверить AwaitingContent, ContentReceived, Processing, Completed, Rejected, Cancelled и эффективный Expired по переходам загрузки. |
| Library, allowance, метаданные и закрытая выдача готового Attachment/PublicationImage, DELETE файла | Свой набор и файлы доступны владельцу с любой текущей ролью. Admin может выбрать владельца. Чужой файл без прав Admin, отсутствующий файл, Pending, Deleted и Avatar по file ID дают 404. Для обычного файла или изображения разрешён повтор DELETE владельцем или Admin. |
| Запись managed usage | Владелец статьи с Author или Admin по действующим правилам Publishing. В каждой роли допустим только Ready файл нужного назначения, принадлежащий владельцу публикации. |
| Выдача через публикацию | Published с точной связью и Ready файлом доступна всем. Draft с такой связью доступен владельцу публикации и Admin. Отсутствующая или удалённая статья/связь, недопустимый контекст и Pending/Deleted файл дают скрывающий 404. Снятие с публикации возвращает правила Draft. |
| Версия и изменение собственного аватара, публичная выдача PNG | Собственное состояние доступно любому вошедшему, без административной подмены. Выдача текущего аватара доступна всем, прежний или отсутствующий аватар даёт 404. |

Moderator получает права только из собственного владения, других выданных
ролей или публичности ресурса. Гость на закрытых маршрутах получает 401.
Матрица использует действительные токены и синтаксически корректные запросы.
Проверки скрывающих отказов сравнивают статус и стабильный код и проверяют
отсутствие байтов, имени, размера, владельца и сведений о черновике.

## Загрузка

| Операция | Результат |
|---|---|
| `POST /media/uploads` | 201 Upload, `Location: /api/v1/media/uploads/{id}` |
| `GET /media/uploads/{id}` | 200 Upload владельцу; состояние неизвестного исхода |
| `PUT /media/uploads/{id}/content` | 204 после сохранения байтов в staging или их точного повтора в `ContentReceived` |
| `POST /media/uploads/{id}/complete` | 202 Upload Processing либо 200 UploadResult |
| `DELETE /media/uploads/{id}` | 204 отмена; повтор терминальной отмены — 204 |

Инициализация принимает `{purpose,name,declaredSize,declaredContentType}`.
`purpose`: `Attachment`, `PublicationImage`, `Avatar`.
Размер непустой: максимум соответственно 52 428 800 / 10 485 760 / 5 242 880 байт.
Имя нормализуется по FR-005. Проверить Cc и U+002F/U+005C в исходной строке,
затем удалить крайние Unicode White_Space. Проверить 1–255 Unicode scalars
и отклонить `.`, `..` и префикс из ASCII-буквы и двоеточия.
Тип для изображений — `image/jpeg`, `image/png`,
`image/webp` и должен совпасть с декодированным форматом. Для произвольных
вложений заявленный тип не является гарантией безопасности; выдача octet-stream.

Обязателен `Idempotency-Key: <UUID>`. Область ключа — текущий владелец.
Повтор с тем же нормализованным payload возвращает прежний Upload и Location
без второго резерва; иной payload с прежним ключом — 409 `idempotency_conflict`.
Для Avatar дополнительно обязателен `X-Resource-Version` из `/me/avatar`:
исходная версия входит в нормализованный idempotency payload и сохраняется
в Upload. После аутентификации владельца поиск прежнего ключа и точного payload
выполняется **до** проверок текущей роли, expiry и текущей версии аватара.
Точный повтор возвращает прежний Upload даже после смены аватара/отзыва роли;
исторический результат не выполняет новую запись. Только новая инициализация
проверяет текущую версию, роль и остаток квоты. Для нового завершения версия
повторно проверяется при commit.
Admin не может подставить другого владельца или назначить чужой аватар.

Обычные загрузки создают, передают и завершают Author/Admin. Собственный
Avatar доступен любому вошедшему. GET и отмена доступны владельцу даже после
отзыва Author.
Admin управляет обычными файлами, но endpoint загрузки всегда создаёт свой файл.
Чужая незавершённая загрузка не становится общим административным каталогом.

Raw PUT принимает `Content-Type: application/octet-stream`. API проверяет
владельца, эффективный срок действия и состояние Upload до чтения тела.
Для активной обычной загрузки перед допуском PUT или повтора API проверяет
текущую роль. Отказ даёт 403 без изменения попытки и резерва. PUT, допущенный
до коммита отзыва роли, может записать промежуточные байты, но новый complete
и переход в Ready снова проверяют права. При другой активной передаче
возвращается 409 `upload_in_progress`. `Processing`
и терминальные состояния, включая эффективное `Expired`, дают 409 `invalid_state`.
После `Completed` точный повтор init возвращает прежний Upload, а повтор
complete возвращает его исторический `UploadResult`.

В `AwaitingContent` только новая передача с действующим fencing может изменить
состояние Upload. Для неё API применяет потолок назначения 50/10/5 MiB и
проверяет фактический размер, в том числе при chunked transfer. Подтверждённое
превышение потолка даёт 413 `request_too_large`. Пустое тело или несовпадение с
`declaredSize` в пределах потолка даёт 400 `validation_failed`. В обоих случаях
API переводит Upload в `Rejected` и освобождает резерв в одном commit. Ошибка
чтения или обрыв частичного тела без установленного нарушения размера оставляет
попытку доступной для повтора до истечения срока.

В `ContentReceived` повтор с теми же длиной и SHA-256 возвращает 204. Иная
длина или SHA-256 в пределах потолка дают 409 `content_conflict`, превышение
потолка — 413 `request_too_large`. Каждый исход сохраняет принятые байты,
состояние и резерв квоты.

Отказ прокси или другого транспорта до передачи запроса API не меняет Upload
и резерв. Такой ответ может иметь собственный формат. При неизвестном исходе
клиент читает состояние через GET и по результату повторяет PUT той же попытки
либо отменяет её через DELETE.

Complete ставит устойчивое задание. 202 не означает готовый файл или применённый
аватар. Пока задание выполняется, повтор даёт 202; после успешного commit —
200 с неизменным UploadResult. `Completed` и historical UploadResult не означают,
что файл всё ещё существует или аватар всё ещё текущий. Повтор не воскрешает
удалённый файл и не назначает прежний аватар. Если ready commit уже произошёл,
потерянный HTTP-ответ не переводит успешную операцию обратно в ошибку.
После аутентификации владельца Completed проверяется **до** текущей роли,
expiry и версии аватара: исторический 200 возвращается и после отзыва Author,
замены аватара или наступления прежнего expiresAt. Для нового перехода действуют
текущие права, expiry и сохранённая ожидаемая версия. Если у активной обычной
загрузки отозваны права, новая попытка complete окончательно переводит её
в Rejected с `errorCode: forbidden`, освобождает резерв в том же commit и
возвращает 403. Worker применяет то же правило перед ready commit.

Upload содержит `id,fileId,purpose,name,declaredSize,declaredContentType,createdAt,
expiresAt,state,result,errorCode`. Состояния: `AwaitingContent`, `ContentReceived`,
`Processing`, `Completed`, `Rejected`, `Cancelled`, `Expired`.
`result`/`errorCode` явно null до соответствующего исхода. UploadResult:
`uploadId,fileId,purpose,completedAt,appliedAvatarVersion` (null для не-Avatar).
Ошибки задания доступны владельцу через state/errorCode; временный storage-сбой
сохраняет возможность автоматического/клиентского повтора, не выдавая Ready.

Expiry наступает при `now >= createdAt + 24h`, включая Processing.
Резерв перестаёт учитываться сразу по DB time, независимо от worker.
GET уже возвращает эффективное Expired на этой границе, даже если фоновая
фиксация/очистка ещё не произошла. Completed, Rejected и Cancelled не превращаются
в Expired по возрасту; исторический успешный результат сохраняется.
Отмена/отклонение также освобождает резерв сразу. Терминальные rejected,
cancelled, expired uploads нельзя завершить. Отмена Completed — 409 `invalid_state`.
Конкурирующий устаревший writer не может отменить expiry или позднее commit Ready.

## Библиотека, квота и закрытое содержимое

| Операция | Правила |
|---|---|
| `GET /media/files` | Ready Attachment/PublicationImage владельца; `page=1`, `pageSize=20`, максимум 100 |
| `GET /media/allowance` | `{limit,used,reserved,available}` в байтах |
| `GET /media/files/{id}` | 200 FileMetadata владельцу/Admin |
| `DELETE /media/files/{id}` | 204 для Attachment/PublicationImage, 409 `file_in_use` при связи с публикацией, 404 для Avatar |
| `GET /media/files/{id}/content?variant=original\|display` | закрытая выдача владельцу/Admin |

`ownerId` в списке/квоте разрешён только Admin; без параметра — текущий владелец.
`page` — целое число от 1 до 2 147 483 647, `pageSize` — от 1 до 100.
Неверное значение даёт 400 `validation_failed`. Каждая страница использует
текущий набор и сортировку `createdAt DESC,id DESC`. Пустой набор и страница
за его концом дают пустой `items` и `hasNextPage=false`. При вставке или
удалении между запросами состав последующих страниц может сместиться.
Ответ страницы: `{page,pageSize,items,hasNextPage}` с фактически применёнными
номером и размером страницы.
Аватары и их представления в библиотеку не входят. Отзыв Author сохраняет
чтение/скачивание/удаление прежних собственных файлов.

Лимит 1 073 741 824. `used` — исходный размер Ready файлов и текущего аватара;
`reserved` — заявленные размеры активных неистёкших uploads; `available` —
`limit-used-reserved`. Производные не прибавляются. При замене аватара новый
upload резервируется при ещё учтённом старом аватаре; льготного превышения нет.
После успешной замены старый размер вычитается в той же транзакции.

FileMetadata: `id,ownerId,purpose,name,size,contentType,createdAt,state,originalUrl,
displayUrl`. Здесь выдаётся только Ready; недоступность не раскрывается через
другой state. Для Attachment original — исходные bytes, display отсутствует.
Для PublicationImage original закрыт, display — очищенный PNG.
У Avatar нет библиотечного original endpoint.

Удаление Attachment/PublicationImage прекращает чтение и учёт квоты в одном
commit. Физическое удаление асинхронно. Повтор DELETE владельцем или Admin
возвращает 204 по tombstone, посторонний получает 404. Действующая связь с
публикацией запрещает удаление. После отвязки Ready файл остаётся в библиотеке.
ID аватара, включая tombstone, возвращает здесь 404 любому вызывающему.
Владелец удаляет текущий аватар через версионированный `DELETE /me/avatar`.

## Связи публикации и доступ читателей

В существующий PublicationWrite добавляются необязательные `coverFileId`,
`inlineImageIds`, `attachmentIds`. При создании пропуск означает null/пустые
массивы. При обновлении пропуск новых полей сохраняет прежние связи;
явный `coverFileId:null` или `[]` снимает соответствующие связи. Повторы ID
в одной роли отклоняются. То же PublicationImage может занимать одну связь
Cover и одну Inline, каждая засчитывается в пределах своей роли.
Пределы: одна обложка, 50 inline images, 20 attachments.
Файлы Ready, соответствующего назначения и владельца публикации.

Связи и текст/поля статьи сохраняются вместе с её версией;
`X-Resource-Version` и существующие permissions сохраняются. Конфликт — 409
без частичных изменений. Удаление публикации атомарно снимает регистрации.
Успешные create/edit/publish/unpublish возвращают `WorkspacePublication` из
снимка своей транзакции. `author.avatar` отражает текущее назначение в том же
снимке, включая `null` при его отсутствии. Формирование ответа после commit
использует этот снимок.

У обложки один источник. Явный внешний HTTPS `coverUrl` снимает управляемую
обложку; `coverFileId` назначает управляемую и снимает внешний источник.
Одновременный non-null `coverFileId` и внешний non-null `coverUrl` — 400.
При пропущенном coverFileId точное эхо текущего управляемого coverUrl сохраняет
связь; другой внутренний media URL нельзя назначить как внешний адрес.
Схема допускает синтаксис относительного управляемого URI-reference; проверка
точного совпадения с текущей обложкой этой статьи выполняется на ресурсе.
Пропуск legacy coverUrl сохраняет прежнее правило очистки внешней обложки,
но сам по себе не снимает управляемую связь. Явный coverFileId:null снимает
её; `coverUrl:null` без нового поля не удаляет управляемую обложку.

Read DTO сохраняют `coverUrl` как effective URL и добавляют `coverFileId`.
Detail возвращает `inlineImages:[{fileId,url,width,height}]` и
`attachments:[{fileId,name,size,url}]`; workspace detail дополнительно отдаёт
`inlineImageIds`/`attachmentIds`. Карточки не раздуваются полными массивами.
Markdown остаётся недоверенным source. Рендерер использует возвращённые явные
связи; обычный текстовый URL не создаёт регистрацию и не предоставляет права.

`GET /publications/{publicationId}/media/{fileId}/content` с
`variant=attachment|display` проверяет текущую доступность статьи и точную связь.
Владелец/Admin имеют доступ и к черновику; остальные — только к опубликованной
статье. `attachment` требует Attachment link, `display` — cover/inline image.
Варианта original у публичного пути нет. В ответах читателя нет ownerId,
закрытых оригиналов или других использований этого файла.

Для любого download API сначала проверяет текущий доступ, затем подготавливает
объект и проверяет его целостность. Перед успешными заголовками и перед
классифицированным 503 из-за ошибки чтения, spool или целостности API заново
проверяет доступ к ресурсу. Если доступ зависит от роли, API читает текущие
локальные роли в том же свежем снимке, что и ресурс. Закрытие публикации,
удаление связи или файла, смена аватара и отзыв роли, лишивший доступа,
дают 404 `resource_not_found` без закрытых метаданных. Уже начатый разрешённый ответ
может закончиться. Скачивание не увеличивает просмотры статьи. Attachment и
original выдаются как `application/octet-stream` с `Content-Disposition: attachment`
и безопасными ASCII `filename` и UTF-8 `filename*`. Display выдаётся как `image/png`.
Все binary ответы содержат `X-Content-Type-Options: nosniff`.
Успешный binary ответ содержит `Content-Length`, равный полной проверенной
длине выбранного объекта; это не заявленный клиентом размер исходника.
Отсутствующий или повреждённый объект готового файла даёт 503
`dependency_unavailable`, если повторная проверка подтверждает доступ.

## Собственный аватар и авторство

`GET /me/avatar` — `{fileId,version,avatar}`: явные null при отсутствии аватара,
но стабильная непустая UUID version существует и для пустого состояния.
Конкурирующие первые чтения не создают разные текущие версии.
Назначение происходит только успешным завершением Avatar upload.
`DELETE /me/avatar` требует текущий `X-Resource-Version`, возвращает 200 новое
состояние. Старая версия даёт 409, включая повтор после потери ответа:
клиент проверяет GET. Удаление уже пустого состояния с текущей версией — no-op.

`GET /avatars/{fileId}/{size}.png`, size 256 или 512, публичен только при текущем
назначении этого файла аватаром. API перепроверяет назначение после попытки
чтения объекта по общему правилу выше. Старый URL сразу перестаёт разрешаться
после commit замены или удаления. No-store укладывается в предел 5 минут. Оригинал
публичного пути не имеет. PNG создан заново без metadata, EXIF orientation
учтён, центральная обрезка допускает увеличение.

`Me` расширяется `avatar` и `avatarVersion`; `AuthorRef` — `avatar`:
null или `{fileId,smallUrl,largeUrl}`. Это текущее состояние, не снимок во время
создания публикации/комментария. Hidden/Deleted комментарии сохраняют
`author:null` и никогда не получают отдельного поля, раскрывающего avatar.

## Новые стабильные ошибки

| HTTP | code | Условие |
|---|---|---|
| 400 | `validation_failed` | имя, размер metadata, пустое тело или несовпадение `declaredSize` при новой передаче в пределах потолка, сочетание cover sources, malformed version |
| 409 | `quota_exceeded` | недостаточный остаток квоты |
| 409 | `idempotency_conflict` | прежний ключ с иным payload |
| 409 | `content_conflict` | иная длина или SHA-256 в пределах потолка после принятия bytes |
| 409 | `upload_in_progress` | действующая передача bytes |
| 409 | `invalid_state` | complete без bytes или в `Rejected`, `Cancelled`, `Expired`, PUT в `Processing` или терминальном состоянии, отмена `Completed` |
| 409 | `concurrency_conflict` | устаревшая версия публикации/аватара |
| 409 | `file_in_use` | удаление используемого файла |
| 413 | `request_too_large` | API установил превышение потолка назначения |
| 415 | `unsupported_media_type` | неверный transport MIME или недопустимое изображение/анимация |
| 503 | `dependency_unavailable` | Garage/DB/spool временно недоступен, целостность объекта нарушена |

401/403/404/405/406 и базовые ошибки сохраняют прежние коды. `errorCode` в
Rejected Upload хранит безопасную причину из этого набора; Cancelled/Expired
различимы по state. Для ошибки фонового назначения из-за смены версии хранится
`concurrency_conflict`; прежний аватар сохраняется.
